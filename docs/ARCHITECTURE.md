## 二、数据在哪，什么能删什么不能删

全部数据在一个目录（默认 `~/.manage-api/`，可用 `MANAGE_API_HOME` 覆盖）：

| 文件 | 内容 | 可重建？ |
|---|---|---|
| `master.key` | **加密主密钥**（AES-256-GCM） | ❌ **绝不能删**。删了所有上游 Key 永久解不开 |
| `db.json` | 站点 / 凭据 / 供给 / 设置 / 各类账本 | 部分可重建（要重新导入） |
| `benchmark.json` | 官方基准价 | 可载入内置参考价 |
| `probe-spend.json` | 探针花费统计 | 可重建 |
| `usage.json` / `usage-detail/` | 用量统计 | 可重建 |
| `daemon.lock` | 实例锁（pid + port） | 自动重建 |

`db.json` 内部结构（按「配置」和「运行期」分）：

| 类别 | 字段 | 说明 |
|---|---|---|
| **配置** | `providers` 站点、`credentials` 凭据（43 个 Key）、`offers` 供给、`settings`、`manualOrder`、`pinnedOffer` | **用户资产，不能随便删** |
| **运行期** | `probes` 探针记录、`routing` 路由决策、`traffic` 流量样本、`errorbook` 错误账本、`faultEvents`/`faultSignals` 故障、`offerStats` 供给统计、`billingSamples` 计费样本、`emptyTurns` 空回合、`monitor` 余额快照、`protocolProbes` 协议记录 | 可清空，会重新累积 |

**这就是为什么「清空数据」有两种含义**——清运行期 ≠ 清配置。需要时只清运行期字段。

## 三、核心概念：供给（offer）

这是整个系统的**最小决策单元**，理解它其它都通了。

```
站点(provider)  →  凭据(credential, 一个 Key)  →  供给(offer)
                                                    = 站点 × Key × 模型 × 分组
```

一个供给 = **「用这个站的这把 Key，请求这个模型，走这个分组」**一条具体路径。

- 5 个站点 × 43 个凭据 × 若干模型 → 展开成 **357 个供给**（你库里的实际数字）
- 网关**永远在供给层面决策**，不在站点层面
- 同一个模型可能有几十条供给，评分后只有少数「能登场」

关键代码：`core/inventory.js`（1951 行，最大的模块，管理供给的全生命周期）

## 四、一次请求的完整链路

入口：`daemon/server.js:4787 handleChatCompletions`

```
1. 鉴权        authorizeGateway()        → [客户端→网关] Key 对不对
2. 分流        免费池 / 付费池            → 免费入口绝不改派到付费
3. 自动路由    pickAutoRoute()            → 是否无视客户端 model 改派
4. 缓存亲和    applyAffinity()            → 该不该为了省缓存而不换人
5. 选路        selectCandidates()         → 准入过滤 + 排序（check）
6. 兜底阶梯    buildLadder()              → 保证非空，逐级往下试
7. 转发        wire.js                    → 发请求、读 SSE、写回客户端
8. 记账        offerStats / usage / traffic → 供下次评分
```

### 第 1 步：鉴权 —— 分清是哪一段的问题

```
daemon/server.js:4000 authorizeGateway()
```

报错**必须标明段位**，因为这个项目有两条独立的 Key 体系，极易混淆：

| 段位 | Key 是什么 | 在哪管 |
|---|---|---|
| **客户端 → 网关** | 网关 Key（`sk-mapi-…`） | 面板 → 网关 |
| **网关 → 中转站** | 各站自己的 Key | 面板 → 站点 → 凭据 |

历史教训：原来只报「API Key 无效」，用户会跑去改中转站的 Key，越改越乱。

### 第 2 步：分流 —— 免费池与付费池严格隔离

```
core/free.js  splitOffers()
```

- 免费入口（`/free/v1` 或 `free/` 前缀）只看免费池
- **默认两边互不回落**：免费用不了就明确报错，不偷偷扣钱
- 只有 `settings.allowPaidFallback` 显式打开才允许「免费不够 → 付费顶上」

设计理由：把免费请求静默改派到付费模型 = 静默扣钱，项目明令禁止。

### 第 5 步：准入 + 排序 —— 两个独立的判断

```
core/router.js  selectCandidates()   (626 行)
```

**这里最容易搞混：「能不能用」和「谁更好」是两套规则，不能混。**

#### (A) 准入（admission）—— 硬门槛，任何档位都不放宽

不登场的理由（`admissionOf`）：

| 状态 | 含义 |
|---|---|
| `slow` | 首字超过用户设的门槛 |
| `suspect` | 结果可疑（掉包/截断） |
| `unstable` | 失败率高 |
| `no-evidence` | 没有可信样本 |
| `cooling` | 冷却中（刚被上游拒过） |
| `broke` | 余额见底 |

用户可以在探针页打开「放行可疑供给」，让 `suspect`/`unstable` 重新登场——
但**首字门槛和冷却不受这个开关影响**，因为它们是显式设置。

#### (B) 排序（decisionMode）—— 四档，只改「谁排前面」

```
core/decision-mode.js  DECISION_MODES
```

| 档位 | 口径 | 适用 |
|---|---|---|
| `value` 性价比（默认） | 价格 ÷ 质量 | 通用 |
| `price` 价格 | 名义单价 | 只要便宜 |
| `speed` 首字速度 | 首字延迟 | 交互式场景 |
| `priceSpeed` 价速比 | 价格 ÷ 首字延迟 | 贵和慢一起看 |

**关键区别**：准入说「能不能上场」，decisionMode 说「上场后谁先上」。
混成一个滑块会导致用户永远说不清自己改的是哪条规则。

### 第 6 步：兜底阶梯 —— 「报错是最后手段」

```
core/fallback-ladder.js  (232 行)
```

**这是 2026-10-31 一次真实故障后重写的，原因值得记住：**

> 实测 357 个供给里 **200 个（56%）没有任何探针记录**。
> 旧逻辑：无探针 → `no-evidence` → 准入拒绝 → 兜底只收 `slow` → 兜不住
> → 候选链空 → 客户端收到 400。
>
> **结果：一个模型看起来有 40 条供给，实际一条都不敢用。**
> 更糟：探针集体失败时（网络抖动/限流），所有供给同时变 no-evidence，整条链瞬间全崩。

现在的原则（用户原话）：「**千万不要让前台客户端报错**」

所以改成：**只要「理论上有机会成功」，就一定要给出候选**，按成功率从高到低排阶梯：

```
不该真排除的：      无探针数据（只是不知道，不是知道它不好）
                    探针说慢（慢 ≠ 不通）
                    失败但已过冷却（现在可能好了）
```

### 第 6.5 步：人工勾选 —— 它压过准入，且只有一份查法

```
core/inventory.js#pinnedOfferIdOf / pinnedOfferStateOf / manualOrderOf
core/route-orchestrator.js#decideRoute（④ 人工勾选不许被阶梯吃掉）
```

2026-11-12 一次性修掉的一族 bug，成因都一样：**同一个「用户指定」被三处各查一遍**。

| 症状 | 根因 |
|---|---|
| 决策页写「当前选 007」，网关一直派 0055 | 勾选那条准入没过（失败率过高/冷却）被阶梯当硬失败踢出链；勾选那条准入过了但排在 `maxPerTier` 之外也会被切掉。两种情况下链里没有它，`applyPinnedChoice` 找不到 → 静默回退自动第一名 |
| 页面写「当前选 秋」，网关一直派 rapid | 勾选那条被「忽略模型」整类挡掉，页面仍显示它生效，且日志每单刷一行「未应用」 |
| 拖拽顺序时灵时不灵 | `pinnedOffer` / `manualOrder` 的键是「点选那一刻界面上的名字」，页面用裸键、网关用身份键、自动路由又一份，写法一变就有一处认不出 |

三条硬规则（改这块之前先看）：

1. **勾选压过准入，但不压过「本次已试过」**。准入是给自动选择用的判据，管不住人手点的；
   人的指定等于「我就要这条，慢/在冷却我也认」。真发失败照旧沿「锁定失败后转移」档往后走。
   唯一的硬限制是同一请求内已试过（防死循环），与 `tierOf` 同口径。
2. **查勾选/查拖拽顺序只调 `pinnedOfferIdOf` / `manualOrderOf`**。查法固定为
   身份键 → 存储键 → 原样键 → 按身份键反查整张表；最后那步是根治，任何写法只要
   归一到同一身份键就认得出，不依赖写入时的拼法。页面、网关、自动路由三处共用。
3. **「勾了但派不到」必须显式告诉用户**。`buildState` 的 decisions 下发
   `pinnedState`（ok/missing/delisted/paused/ignored/not-in-model + 人话原因）与
   `pinnedApplied`；页面据此挂「勾选未生效」红标，而不是继续假装它生效。

另外：决策页的重排档位必须与网关同源——都是
`routingTargetOf(...).decisionMode || settings.decisionMode`。只读全局设置的话，
选了一个「最便宜」路由组之后页面按全局档排、网关按组档排，两边各给一个「当前选」。

### 第 7-8 步：转发与记账

```
core/wire.js (523 行)      发请求、读流、把正文/工具调用递给客户端
core/usage.js / usage-ledger.js  用量记账
core/offer-stats.js        供给统计（喂给评分）
```

## 五、三套「证据系统」—— 这是最混乱的地方，必须分清

项目里同时存在**三类独立的质量证据**，它们回答不同问题，**不能互相替代**。
这是历史上最容易混淆的部分。

| # | 系统 | 回答什么 | 什么时候跑 | 成本 | 代码 |
|---|---|---|---|---|---|
| 1 | **探针** | 「模型老不老实」 | 定时 / 手动 | 花 token | `core/probe.js` `protocol-probe.js` |
| 2 | **真实流量** | 「实际用起来怎么样」 | 每单自动 | 免费 | `core/quality-signals.js` `real-drift.js` |
| 3 | **外部故障上报** | 「别人观测到它挂了」 | 被动接收 | 免费 | `core/failover.js` `fault-signal.js` |

### 系统 1：探针（probe）

#### 1a. 普通探针 —— 测「偷工减料」

```
core/probe.js (349 行)
```

测什么：
- **指纹** —— 让它重复一段特定文本，看是否真照做（识别降智换模型）
- **截断** —— `max_tokens` 是否被悄悄压低
- **计费** —— 报的 token 数是否虚高
- **缓存** —— 缓存数字是否真实

关键设计：**探针分与真实分彻底分离**（提交 `ace7128`）。
探针测的是「模型诚实度」，不掺入真实速度，避免两个口径互相污染。

#### 1b. 协议探查 —— 测「这个站到底支持什么协议」

```
core/protocol-probe.js (2160 行，最大的单文件)
```

回答三个问题：

1. **表面协议** —— 接不接受 Chat Completions / Responses / Anthropic / Gemini？
2. **真实协议** —— 收下了，背后是原生实现还是翻译层？
   - 办法：验证原生协议才有的能力（Responses 的 `previous_response_id`、
     Anthropic 的 `tool_result` 块）
   - **翻译层能装出外形，装不出这些**
3. **能不能干活** —— 由 `protocol-verdict.js` 翻成「能导进哪个工具、导错会怎样」

配套模块：

| 文件 | 作用 |
|---|---|
| `protocol-catalog.js` (199) | 四种协议「原生应该有什么」的字典，界面与记录页共用 |
| `protocol-verdict.js` (242) | 「哪几项红了」→「能干什么」 |
| `protocol-records.js` (113) | 结果落库到 `db.protocolProbes` |

**边界**：这里只发探测请求，**不写 db、不参与评分**。超时按「无法判定」处理，
不把网络问题算成站点缺能力。

#### 1c. 连接层预检 —— 花钱之前先筛

```
core/probe-preflight.js (260 行)
```

L1/L2 预检：**在花真钱之前**先把「根本连不上的站」筛掉。

#### 1d. 探针花费账本

```
core/probe-spend.js (253 行)
```

只统计「探针自己发出去的那几个请求」花了多少钱，与业务花费分开。

### 系统 2：真实流量信号

```
core/quality-signals.js (113)  探针之外的第二类完整性证据
core/real-drift.js (515)       真实价速比漂移监视
```

**为什么需要它**：探针不带 `tools`，所以「带工具时工具调用坏了」探针永远显示健康。
这个病只有真实流量能发现。

`real-drift.js` 的具体机制：
- 网关每单成功的真实请求（首字 + usage）顺路记进**内存快窗口**
- 成本在 tick 里按报价估算
- 判断「探针说最优，但真实负载已漂移」→ 加入**降级名单**
- 降级名单递给热路径重挑：**探针说最优但真实已漂移的站不能选回来**

### 系统 3：外部故障上报 + 本机故障信号

```
core/failover.js (141)       接收外部监控的真实故障上报
core/fault-signal.js (404)   本机诊断向外报告故障的统一出口
core/fault-triage.js (268)   判断「用户到底受没受影响」再决定要不要上报
core/error-fingerprint.js (143)  上游报错归一化成可聚合的指纹
```

**为什么要有 triage（研判）**：一次请求失败了，但用户可能已经靠重试拿到了结果。
不加研判就上报，会把「虚惊一场」算进故障，误伤好站。

## 六、自动路由 + 缓存亲和（你最关心的部分）

### 6.1 自动路由在做什么

```
core/auto-route.js (402 行)
```

**开着的时候，网关不再理会客户端请求里的 `model` 字段**，一律改派「当前决策档位
下全场最优的那个模型」：

1. 每个模型先取它自己准入通过的最优供给
   （口径与网关派活完全同一份：`selectCandidates` + `admissionOf`）
2. 再按 `decisionMode` 的标量（`tierMetricOf`）跨模型比，最小者胜
3. **模型归属哪个站、哪个分组一律不管**——决策侧重只回答「谁最好」

### 6.2 迟滞（防抖）—— 为什么不频繁换

```js
AUTO_ROUTE_SWITCH_GAIN = 0.15   // 新模型要好 15% 以上才换
```

**反复横跳对用户的干扰（客户端上下文里模型突然变了）远大于那一点收益。**

所以只有当：
- 新模型指标比现役好出 **15%** 以上，**或者**
- 现役的供给全下线了

才切换。

**例外**：切档（`decisionMode` 变更）是用户显式意图，走 `force` 重选，不受迟滞约束。

### 6.3 故障转移

```
core/failover.js
```

外部监控上报的真实故障**比探针准**——被命中的供给直接失去「最优」资格
（哪怕探针说它健康）。

- 现役被摘时**立刻换人**（`reason='failover'`，不受迟滞：真故障不等人）
- 记住 `failoverFrom`
- 故障到期后供给自动恢复参选；若它仍是全场第一，提回来（`reason='fault-recovery'`，
  同样不受迟滞——重回第一本身就是明确信号）

### 6.4 缓存亲和 —— 借鉴 Magpie 的核心洞察

```
core/affinity.js (280 行)
```

**这是从 Magpie 抄过来的机制，解决原设计的盲点：**

> 自动路由原先只看「谁更好」（价格/速度/性价比），**完全没把「换人」的代价算进去**。
>
> 而真实成本里有一项占比极高：**上游的 prompt 缓存**。
>
> KV/prompt 缓存绑在「模型 + 上游分组 + 账号」这个组合上。一旦改派：
> - 客户端那几十万 token 的上下文要在新模型上**从零重算**
> - 缓存读取那部分账单（通常占输入 token 的 80~95%）**直接归零**
> - 首字延迟从「几乎不用算」变成「全量预填充」

所以：**宁可不用最优，也不废掉上游缓存。**

实现要点：
- 算「这段对话的指纹」（`conversationFingerprint`）
- 判断这一单是不是「同一个 turn 内的后续」（判据：消息里有 assistant/tool 往返）
- 拿不到指纹就不做亲和，**行为与旧版完全一致**（向后兼容）
- 结果：`reason='kept-best'` 表示「为了保缓存而没换人」

### 6.5 ⚠️ AutoThink 现在是关掉的

```js
// core/auto-route.js:69
export const AUTO_ROUTE_CLIENT_SWITCH = false
```

**这不是 bug，是有意设计**（2026-10-30）：

> 接管会在模型之间反复切，而模型的 KV 缓存是绑在模型+上游分组上的——每换一次，
> 客户端那几十万 token 上下文就要重新算一遍，**缓存命中率暴跌**，
> 省下的差价远不够赔变慢与缓存重建。**路由逻辑改好后再打开。**

影响范围（必须分清）：

| 能力 | 状态 |
|---|---|
| 面板开关（`PATCH /api/settings` `autoRouteEnabled`） | ✅ **可用** |
| 挑选 / 迟滞 / 轮巡 / 漂移转移 | ✅ 全部保留 |
| 客户端点名 `model: "AutoThink"` | ❌ 关闭 |
| `/v1/models` 清单里出现 `AutoThink` | ❌ 关闭 |

**两边必须是同一份判定**，只关一边会得到「清单里看得到、点了没反应」
或「看不见、但手写 `AutoThink` 居然能开」，两种都更让人糊涂。

要打开：改 `AUTO_ROUTE_CLIENT_SWITCH = true`，同时 `daemon/server.js` 的模型清单会跟着露出来。

## 七、评分是怎么算的

```
core/score.js (661 行)
```

**两个维度分开算，不混成一个加权和**（这是刻意的）：

| 维度 | 含义 | 数据来源 |
|---|---|---|
| `availability` | 连得上吗、成功率高不高 | 探针 + 真实流量合并，只算真正故障 |
| `integrity` | 连上了，但结果可信吗（掉包/截断/虚报） | **只来自探针** |

**额度不足 / 限流 / 模型不在分组不算「连不上」**——它们让供给进冷却，
不拉低可用率（详见 `core/failure.js`）。

路由时的用法：**硬约束 + 有效成本**

```
任一维度不达标 → 直接排除
剩下的 → 按 价格 ÷ 质量 排序
```

### 时效性

```js
DEFAULT_MAX_AGE_MS = 6 * 3600 * 1000        // 评分 6 小时过期
DEFAULT_TRAFFIC_MAX_AGE_MS = 3600 * 1000    // 真实流量窗口 1 小时
MIN_SAMPLES_FOR_VERDICT = 3                 // 至少 3 个样本才敢判「确定坏」
```

- **过期的评分一律不放行**（昨天健康、今天掉包的站不能被继续用）
- 样本不足 3 个时，失败只说明「还没测出来」，判 `unknown` 而非 `unstable`
  ——否则探针间隔 6 小时、一轮只测到 1 次失败，这条供给会一直挂红

## 八、后台调度器全景

启动编排在 `daemon/index.js`。**7 个后台任务**，各管一件事：

| 调度器 | 文件 | 频率 | 职责 |
|---|---|---|---|
| 探针调度 | `scheduler.js` (232) | 每分钟检查 | 哪些供给距上次探测超过间隔，挑最多 10 个去探 |
| 自动路由轮巡 | `autoprobe.js` (243) | 活跃期 | 自动路由接真实流量时，保证评分新鲜 |
| 探针执行 | `probe-runner.js` (203) | — | HTTP 路由和定时调度共用同一份逻辑 |
| 监控采集 | `monitor-runner.js` (179) | 定时 | 余额 / 公告 / 倍率，各自独立失败 |
| 漂移监视 | `drift-watcher.js` (354) | tick | 真实价速比漂移 + 故障转移状态机 |
| 体检执行 | `checkup-runner.js` (144) | **仅手动** | 诊断页「体检」按钮，**绝不自动打上游** |
| 改道复检 | `detour-runner.js` (180) | 20 分钟 | 被挂起的站悄悄摸一次，连续正常就切回流量 |

### 设计要点：为什么用「检查 + 到期判断」而不是长间隔 `setInterval`

> 这样改配置能立即生效，也不会因为一次探测耗时较长而错过下一轮。

### 为什么 `autoprobe` 要单独存在

> 探针定时任务可能被关掉（省钱），但自动路由在接真实流量时，评分必须新鲜——
> 自动路由每单都按评分挑全场最优，**拿几小时前的首字/指纹派活等于闭眼开车**。

### 为什么 `checkup-runner` 要独立

> 诊断页平时是「读账本」，纯本地零请求；只有用户亲手点「体检」才允许真的打上游。
> **这条边界必须在代码结构上就看得见**，避免哪天被别的地方顺手调用变成定时刷上游。

## 九、诊断与异常

```
core/diagnosis.js (418)   诊断引擎：账本原始信号 → 说人话、带证据、指处方的结论
core/anomaly.js (316)     异常诊断：没报错，但表现不对劲
core/empty-guard.js (406) 空回合守卫：「上游这一轮到底说话了没有」
```

### 空回合守卫（empty-guard）—— 一个很有价值的设计

**问题**：上游返回了 200，但一个 token 都没吐（空回合）。客户端看到的是「成功但没内容」。

**做法**：
1. 判断「这一轮到底说话了没有」
2. 没说话 → 自动再问一遍（换站）
3. 如果带 `tools` 时工具调用坏了 → 挂起这个站，交给 `detour-runner` 每 20 分钟复检
4. 连续正常几次 → 悄悄把流量切回去

**为什么不能复用探针**：
> 探针测的是「模型老不老实」（指纹/截断/计费），**根本不带 tools**，
> 所以它一直显示健康——而这里的病恰恰是「带 tools 时工具调用坏了」。

## 九·五、级联失败防线 —— 「一开自动路由就连环崩」是怎么被堵住的

> 这是作者最痛的一段历史：**「开自动路由，一开就崩，一开就崩」**，最后心态爆炸。
> 这一段专门记录：**当初为什么会崩**，以及**现在有哪些闸门**。

### 9.5.1 崩的机理：一条正反馈回路

```
真实请求失败
   ↓
诊断系统判定 impact（blocked / degraded / none）
   ↓ 上报故障
自动路由把该供给剔除出「最优」→ 换人
   ↓ 换了人，新供给没有缓存 / 没被探过
新供给也失败（原因可能完全不同）
   ↓ 再上报
剔除范围扩大 …
   ↓
可用供给越来越少 → 落到更差的供给 → 更容易失败
   ↓
**整条链自己把自己吃干净**
```

**关键**：这个回路不需要任何单个 bug 就能跑起来。**只要「上报」和「剔除」的
粒度和门槛不对，它就会自激。**

### 9.5.2 现在的五道闸门

#### 闸门 1：`isFaulted` 只降级，**不拉黑**

```js
// core/router.js:351-353
// isFaulted —— 可选谓词（failover.js#faultMatcher）：外部监控上报的真实故障。
// 降级不拉黑：故障转移不是准入判定，探针说健康就照样 admission.ok，
// 只是同类里靠后 + 自动路由不把它当「最优」；故障到期自动恢复
```

**这是最重要的一道闸。** 含义：

| | 故障会不会影响 |
|---|---|
| 准入 `admission.ok` | ❌ **不影响**（探针说健康就还是健康） |
| 排序（同类靠后） | ✅ 影响 |
| 自动路由的「最优」资格 | ✅ 影响 |
| 兜底阶梯能否用它 | ✅ **能**（所以永不报错） |

**推论**：哪怕全场供给都被标了故障，`buildLadder` 仍然兜得住，
客户端不会收到 400/502。**「全崩」在结构上被堵死了。**

#### 闸门 2：故障定位「越精确越优先，宁可少拉黑不可多拉黑」

```js
// core/failover.js:67-73
export function addFaultReport(failover, { offerId, modelKey, kind = 'runtime', ... } = {}) {
  const offer = typeof offerId === 'string' && offerId ? offerId : null
  const record = {
    ...
    offerId: offer,
    modelKey: offer ? null : (modelKey || null),   // ← 有 offerId 就强制清空 modelKey
```

`faultMatcher` 的匹配规则是：

```js
(r.offerId && r.offerId === offer.id) ||
(r.modelKey && r.modelKey === (offer.modelKey || offer.upstreamName))
```

**如果两个字段都留着，一次失败会把同款模型的全部供给一起摘掉**——这是典型的级联放大。
代码用「二选一」直接掐掉了：有精确的 `offerId` 就不要 `modelKey`。

**实测验证**（3 条同款模型供给，只上报其中 1 条）：

```
o_A: ❌被摘      ← 只有它
o_B: ✅仍可用
o_C: ✅仍可用
```

#### 闸门 3：研判分级 —— `none` 绝不惊动路由

```js
// core/fault-triage.js 头部
//   none     —— 用户完全无感。换站成功了、零内容断流后重放成功了。
//               这一类**绝不能上报**：自动路由一收到故障就会把供给剔除十分钟，
//               拿无感故障去报，等于让它在健康供给之间瞎折腾，比不报更糟。
//   degraded —— 用户拿到了结果，但明显变差。**攒够才报**（10 分钟内 2 次）。
//   blocked  —— 用户真的没拿到东西。**立即报**，一次就够。
//
// 关键取舍：宁可晚一拍上报，也不要误报。
// 故障转移的代价是把一条可能健康的供给剔出十分钟；
// 而「多转一小会」的代价只是几百毫秒。用户体验的天平偏向前者。
```

代码里的落地（`server.js:4735`）：

```js
// 用户完全无感且没换过站：什么都不记（不然每单都写库）
if (impact.impact === IMPACT.NONE && attemptCount <= 1) return
```

#### 闸门 4：客户端自己断开 ≠ 站方故障

```js
// server.js:4706-4716
// 客户端自己断开的：既不算故障，也不能当作「无感截流」白白吞掉。
// 这里必须做聚合：客户端取消是家常便饭（agent 到点取消、用户按 Esc），
// 每次都新写一条会把事件账刷满。
if (outcome === OUTCOME.CLIENT_ABORTED) { ... 记一条 status='ignored' ... return }
```

**这条是真实 bug 的修复**（提交 `ff07431`）：

> `fix: 客户端自己断开被记成站方断流，断流率虚高还误报剔了好站`

**这正是级联的一个典型触发点**：agent 频繁取消 → 被误判成站方断流 →
好站被剔除 → 落到差站 → 更容易失败 → 更多取消被误判 → **自激**。

#### 闸门 5：全场无可用时「交回去报错」，不瞎折腾

```js
// core/auto-route.js:270-271
// 全场没有一个能登场的模型：交回调用方走正常报错，记录原样保留
if (!best) return null
```

实测：把所有 9 条供给都上报故障后，`pickAutoRoute` 返回 `null`，
网关按原模型走正常路径（而那条路径有兜底阶梯兜着）。

### 9.5.3 还有哪些「有限但存在」的扰动

这道防线不是无限的，下面这些**设计上允许**，知道就好：

| 现象 | 机制 | 衰减 |
|---|---|---|
| 供给被剔除 | `FAULT_HOLD_MS = 10 分钟` | 到点自动恢复参选 |
| degraded 上报 | 10 分钟窗口内需 2 次 | 单次抖动不报 |
| 漂移转移 | `drift-watcher.js` 有冷却 | 冷却期不再转移 |
| 供给冷却 | `classifyFailure` + `cooldownUntil` | 按失败类型不同 |
| 空回合 | 按耗时分档重试（≤5s 给 2 次，>40s 给 0 次） | 有上限 |

**注意**：这些是「同时生效」的。极端情况下一条供给可能同时处于
「故障剔除 + 冷却 + 漂移降级」，此时**它仍可被兜底阶梯使用**（闸门 1），
只是不会被当作「最优」。

### 9.5.4 自检清单：怀疑又出现级联时

```bash
# 1. 看有多少供给被故障标了，是不是同款模型全被牵连
curl -s -H "Authorization: Bearer <lan-token>" http://127.0.0.1:4319/api/state \
  | node -e "let s='';process.stdin.on('data',d=>s+=d).on('end',()=>{
      const d=JSON.parse(s);const r=d.failover?.reports||[];
      const act=r.filter(x=>x.status==='active');
      const byOff=act.filter(x=>x.offerId).length, byModel=act.filter(x=>x.modelKey).length;
      console.log('活跃故障:',act.length,'| offerId级:',byOff,'| modelKey级:',byModel);
      if(byModel>0) console.log('⚠️ 存在模型级故障，会牵连同款所有供给');
    })"

# 2. 看事件账里「吸收 vs 已上报」的比例（absorbed 多说明研判在起作用）
#    诊断页 → 事件账

# 3. 看自动路由 pick 是不是在短时间内反复变
#    智能决策页 → 切换记录 / 决策日志
```

**判定标准**：
- `absorbed` 远多于 `sent` → 研判正常在工作（好事）
- `modelKey` 级故障 > 0 → 需要看是不是误报（会牵连同款）
- pick 在 1 分钟内变化多次 → 迟滞没生效，查 `AUTO_ROUTE_SWITCH_GAIN`

## 十一、为什么你会觉得乱 —— 五个真实原因

这不是错觉，是项目演进留下的客观复杂度：

### 1. 探针分成了四个层次，但都叫「探针」

| 层 | 文件 | 做什么 |
|---|---|---|
| 连接预检 | `probe-preflight.js` | 花钱前筛掉连不上的 |
| 质量探针 | `probe.js` | 测偷工减料 |
| 协议探查 | `protocol-probe.js` (2160行) | 测协议能力 |
| 花费账本 | `probe-spend.js` | 统计探针花了多少钱 |

**它们不是同类东西**，只是都归在「探针」页附近。

### 2. 三套质量证据并存，且不能互相替代

探针 / 真实流量 / 外部上报——回答的是不同问题（见第五节）。
历史上可能有人以为「有探针就够了」，于是产生了「探针健康但实际不能用」的 bug。

### 3. 自动路由重写过至少三次

从提交历史看：
```
2d0974f feat: 自动路由重构——兜底阶梯保证不报错，余额阈值自动切换，探针经标定校正
01619c0 feat: 缓存亲和——自动路由不再只看「谁更好」
b5d488c fix: 自动路由入口先收起——接管频繁换模型，缓存命中率被打崩
d18fcaf feat: 自动路由接管时模型清单只出一个虚拟模型 AutoThink
```

**每次重构都留下旧代码的痕迹**（比如 `router.js` 和 `route-orchestrator.js` 并存）。

### 4. 「准入」和「排序」长期被混为一谈

这是设计上最容易被误解的地方（见第 5.5 节 A/B）。
一个开关如果同时影响两件事，用户就永远说不清自己改了什么。

### 5. 开关太多，且分散

主要开关：

| 开关 | 位置 | 影响 |
|---|---|---|
| `decisionMode` | 智能决策页 | 排序口径（四档） |
| `autoRouteEnabled` | 智能决策页 | 是否接管 |
| `affinity` | 设置 | 缓存亲和档位 |
| `allowPaidFallback` | 设置 | 免费不够能否用付费 |
| 放行可疑供给 | 探针页 | 准入门槛 |
| 首字门槛 | 探针页 | 准入门槛 |
| 慢速档位 | 设置 | 准入 |
| `AUTO_ROUTE_CLIENT_SWITCH` | 代码常量 | 客户端能否点名 AutoThink |
| 局域网访问 | 网关页 | 网络监听 |

## 十三、关键常量速查

```js
// 自动路由
```

## 十四、想继续改动时，先读这几段注释

这个项目的代码注释质量很高，**改任何一块之前先读它的文件头**，里面通常写了
「为什么这样做」和「踩过什么坑」：

| 想改什么 | 先读 | 关键词 |
|---|---|---|
| 选路规则 | `core/router.js` 头部 | 准入 vs 排序 |

| 自动路由 | `core/auto-route.js` 头部 | 迟滞、failover、免费池边界 |
| 缓存亲和 | `core/affinity.js` 头部 | 模仿 Magpie 的原因 |
| 评分 | `core/score.js` 头部 | 两维度分开算 |
| 探针 | `core/protocol-probe.js` 头部 | 表面协议 vs 真实协议 |
| 局域网 | `daemon/lan.js` 头部 | 为什么不用 0.0.0.0 |
| 工作树限制 | `daemon/index.js:40-70` | REAL_PORT 保护 |
