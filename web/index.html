ManageAPI

个人专属API网关

概览

通知

ManageAPI 解决一个问题：你买了几个 AI 中转站，但不知道哪个更划算、哪个在偷工减料。 它把这些站放在一起比价、定期检测质量，然后用一个本地网关替你自动选站。 全部在本机运行，数据不出本机。

快速开始

  1. 站点 页添加中转站（地址结尾要带 /v1），粘贴它的 Key
  2. 点 一键同步：拉模型、读余额、识别分组一次跑完；没填「令牌」时跳过识别分组
  3. 同步没认出分组，就点 导入倍率，在分组列表里手动选你买的那个
  4. 缺官方价的模型，去 基准价 页补上，或者载入内置参考价
  5. 去 探针 页跑一次检测，让程序知道哪些站可信
  6. 程序会按评分体系自动决定用哪个站，也可以在 智能决策 页手动调整先后
  7. 去 网关 页复制地址和 Key，填进 DSH 等 agent 平台
  8. 界面右上角可以切换中英文，选择会记住

各页面怎么用

概览

打开就能看的总结页，不需要填任何东西。
· 一句话结论 —— 你在用的那个模型，现在哪家最便宜、省多少
· 四个指标 —— 站点数、模型供给数、可比较的模型数、最大价差
· 需要关注 —— 探针判定有问题的站，按站聚合，写明原因
· 站点排名 —— 按长期评分排序，绿点健康、黄点需关注、红点不稳定

站点

录入中转站和 Key 的地方，同时也是监控页：上方是余额曲线、倍率变动和上游公告，下方是站点卡。 一个站可以挂多个 Key。
· 名称 —— 随便填，只用于你自己识别
· 地址 —— 中转站给你的 API 地址，结尾必须带 /v1 （如 https://api.example.com/v1）
· 类型 —— 不确定就选「不确定」，不影响功能
· Key —— 粘贴完整的 sk-...，加密存储，界面只显示尾号

每个站点卡片上有一排按钮：

· 一键同步 —— 同步模型 → 读余额 →（有「令牌」时）识别分组，串着跑完；某一步失败不影响其他步骤。
· 密钥 —— 展开这个站的 Key 列表：加 Key、删 Key、看每把 Key 绑的分组。
· 分组倍率 —— 展开分组倍率，改倍率或恢复站点值。详见下面「分组」一节。
· 导入倍率 —— 读不到后台时的手动方案：列出该站所有分组，你选一个。
· 用量核对 —— 用管理令牌拉站方记录的消费，和我们的估算对比。
· 导出配置 —— 生成 OpenAI 兼容的配置片段，方便复制到客户端。
· 令牌（在站点卡片上）—— 站点后台的登录令牌，用来读余额、用量和识别分组。一个后台账号填一次，整站通用；不参与对话。
· 分组（在 Key 那一行）—— 显示这把 Key 属于哪个分组，点它也能打开选分组。

令牌怎么拿：浏览器登录站点后台 → F12 → Network → 点任意 /api/v1/ 开头的请求 → 复制 Request Headers 里的 Authorization 值（去掉 Bearer 前缀）。 令牌会过期（一般 7-30 天），失效后重新复制。

界面致谢：站点卡的版式（渠道卡、分组胶囊、工具栏）参考了 bejix/upstream-ops 的设计，只借版式；数据与交互都是本项目自己实现的。

分组

中转站的计费公式是 模型原价 × 分组倍率。倍率 0.1 就是打一折，0.3 是三折。
「分组」就是你买的那一档——同一个站常常有十几个分组（特惠池、企业通道、按次计费、 某个模型专用的高价组），同一个模型在不同分组里价格能差好几倍。

为什么必须你自己选？因为「你在哪个分组」是商务事实，API 读不出来。 Key 只能告诉你「能调用哪些模型」，不会告诉你「属于哪一档套餐」。 工具能列出所有分组和倍率，但最后一步得你点。

点「导入倍率」之后会发生什么：
① 弹出该站所有分组，每个后面标着倍率和能覆盖你几个模型，能用的排在前面
② 你选中自己买的那个，点「应用倍率」
③ 这个分组会记在 Key 上，倍率写进下面所有模型，比价 / 决策 / 路由立刻同步
④ 下次再点「导入倍率」，会默认选中上次那个

数据从哪来：有「令牌」时读 /api/v1/channels/available（数据最全， 不要求站开广场）；没令牌则回落「模型广场」。两条路都不通会直接告诉你原因。

分组倍率那几行怎么看：
· 标 站点值（绿）—— 和站点公布的一致，没动过
· 标 自定义（黄）—— 你手改过，旁边会写出站点原本是多少
· 标 混合 —— 这个分组下的模型倍率不一致（单独改过某几个）
· 直接改那个输入框就是自定义倍率，改一次该分组下所有模型一起变
· 出现「恢复」按钮时点一下，回到站点公布的值；顶部「全部恢复为站点值」是整个站一起还原

自己调倍率有实际用处：比如站方标的 0.15 你觉得有水分，按「用量核对」算出来实际是 0.18， 就手动改成 0.18，比价结果才准。

怎么删掉一个分组：卡片「分组」那一行的胶囊后面有个小垃圾桶图标，「分组倍率」该行末尾有「删除」， 比价表分组列也有删除按钮。两种来源后果不同：
· 比价页「＋」复制出来的分组 —— 没有对应 Key，删除时连它下面的模型记录一起删，删完就没了
· Key 自带的分组 —— Key 保留，只清掉分组归属；之后在 Key 那一行点「选分组」重新导入， 模型和倍率会一起回来（不需要先手动同步）

看某个分组里到底有哪些模型：点站点卡上的分组胶囊（或「分组倍率」那一行的「N 个模型」）， 中间会弹出一张卡片，列出这个分组同步到的全部模型和实际价（已乘倍率）。 被忽略的模型也在清单里，标着「已忽略」；已经下线的模型不显示。Esc 或点卡片外的背景关闭。

免费

中转站的免费模型和 Agent 平台的免费积分，单独收在一页，不参与付费比价，也不参与自动选站。 页内分两栏：中转站免费模型 和 平台积分。

中转站免费模型：实际价为 0 的模型，按指纹 / 未截断 / 额度耗尽 / 评分过期做闸门， 质量不达标就整个排除，不给「便宜但烂」留位置。

平台积分：WorkBuddy / CodeBuddy / ZCode 这类 Agent 产品的免费额度。
· 连接 —— WorkBuddy / CodeBuddy 点「连接」授权后自动读积分。接口是平台给自家 IDE 用的， 标了「实验性」，平台升级后可能失效；失效只是读不到数据，不影响其他功能
· 签到 —— 只有实现了自动签到的平台才显示这个按钮；签到会真实请求平台接口，成功才写账本， 同一天重复点只算一次。手动平台和 ZCode 没有自动签到，不会显示这个按钮
· 账号 —— 一个平台可以挂多个账号，卡片上能切换活跃账号、删除账号
· 刷新 / 诊断 —— 重新读额度；字段对不上时，把平台原始返回复制出来定位
· 剩余 指本周期还能用多少，不是套餐总量；重置时间与一次性赠量分开写

免费池只有显式使用时才会被调用：地址换成 http://127.0.0.1:4319/free/v1， 或者模型名前缀 free/。免费池用尽返回 402，不会静默回落到付费。

比价

同一个模型在不同站的价格横向对比。
· 搜索框 —— 输入模型名过滤，右边显示「N / M 个模型」
· 缓存 —— 单独一列：最近一次探测的缓存命中率，没探过显示「—」
· 模式 —— 「倍率 / 价格」二选一，决定这一行按哪种方式计价
· 输入价 / 输出价 —— 「价格」模式下直接填单价，失焦即保存
· 倍率 —— 「倍率」模式下填：实际价 = 基准价 × 倍率，不用再填单价
· 「＋」 —— 按当前行复制一条，给同一个模型在另一档套餐里单独记价（建出来的分组没有对应 Key）
· 垃圾桶按钮 —— 删掉这一行所属的分组（Key 保留，可重新导入）
· ¥/百万 token —— 综合成本，输入按 25%、输出按 75% 加权（权重可在左下角调）
· 价差 —— 比最便宜的贵多少百分比

模式是显式开关，只有当前模式的输入框可编辑。从「倍率」切到「价格」时，程序会把当前折算价 种进输入框，不会因为切模式让这条供给变成「未定价」而消失。

行里的标记：「最便宜」是该模型当前最低价；「可疑」是探针判定不可信的站， 价格照常显示但不参与推荐；「超时」是首字延迟超过你设的上限。 缓存命中率在单独的「缓存」列；综合成本下方的小字是空闲时段价。

一个站挂了多个分组时，同一个模型会出现在同一列的多行里，行内标着是哪个分组。 想给某个模型单独加一个分组，点行尾的 「＋」 复制一条再改；不想要了在「站点」页把它删掉。

智能决策

看路由会选谁，也能手动干预。每个模型一张表：
· 绿底行 —— 当前会选中的那个站
· 有效成本 —— 价格 ÷ 质量，越小越优先
· ↑↓ —— 调整「可用」候选的先后，改完立即生效
· 恢复自动 —— 清掉手动顺序，回到按有效成本排

手动顺序只影响「可用」的那几条。不可信、太慢、评分过期的站默认排在后面， 你拖不动它——可用性是硬判断，不能被手动覆盖。 如果你确实想让可疑的站参与竞争，去探针页打开「放行可疑供给」，它们会正常参与排序， 状态列会标出「已放行」。

探针

检测站有没有偷工。每个模型可以单独点「探测」，也可以点「探测全部」。
· 指纹 —— 要求精确输出固定内容，返回不对说明可能被掉包
· 截断 —— 要求数到 120，没数完说明上游压低了 max_tokens
· 计费 —— 返回的 prompt_tokens 远超实际请求规模，说明用量虚报
· 缓存 —— 同一段长前缀连发两次，看第二次命中多少（这一步要发 2 个请求）
· 身份自述 —— 问它「你是什么模型」，结果只记录、不评分。 因为模型自述本来就不可信，同一个模型换个说法很常见，拿它扣分误伤太多。

点表格里任意一行会展开，能看到质量是怎么算出来的，以及最近一次探测的原始返回证据。

顶部设置项：

· 自动探测 —— 设间隔后后台定时跑。默认 1 小时，可以关掉。模型多的话建议设长一点， 每次探测都要花一点 token。
· 评分有效期 —— 超过这个时间没重新探测，评分就作废。（作废不等于不能用：详见下面的「决策」）
· 放行可疑供给 —— 默认关闭。关闭时，探针判定可疑（指纹不符 / 截断 / 虚报）的站 不登场；打开后它们按有效成本正常参与竞争。

打开这个开关要清楚代价：可疑的站仍然按「价格 ÷ 质量」排序——质量差一半，成本就翻倍， 所以只有便宜到足够多才会被选中。但它确实可能给你返回掉包或截断的结果。 省钱优先就打开，输出可信优先就关着。首字门槛在「智能决策」页，是独立设置，不受这个开关影响。

网关

一个地址接管所有站，客户端只填一个 Key。
· 地址 —— http://127.0.0.1:4319/v1
· Key —— sk-mapi-...，点「新建 Key」可以给每个客户端建一把
· 月限额 —— 建 Key 时可设月度 token 上限，超了返回 429
· 轮换 —— 某把 Key 泄露了单独换，不影响其他客户端

最近请求表记录每次路由：选了谁、试了几次、耗时多少。 点开能看到完整的候选排序和失败原因。

用量

· 范围 —— 7 / 30 / 90 天切换
· 按天柱图 —— 柱高是 token 总量，悬停看当天明细
· 按 Key / 模型 / 站点 —— 三张表，看谁用的、用的什么、实际跑在哪家

只有经过网关的请求才计入。如果你在站上直接用，或别的客户端没走网关，那些不会算进来。

基准价

倍率换算的参照物，本质就是「官方价」：实际价 = 基准价 × 倍率。 某个模型没有基准价，它的倍率就没法换算成钱，只能填绝对价。三个来源：
· 从站点导入官方价 —— 选一个站，一键拉取。有「令牌」读可用渠道、没令牌读模型广场。 只补空缺，不覆盖你已有的
· 以此站已填价为准 —— 把某个站已经填好的实际价整体设为基准，适合你确信它没虚标
· 载入内置参考价 —— 工具内置的一份官方价，价格常变，务必核对

表格里可以直接改价格。「空闲输入 / 空闲输出」是峰谷定价用的（比如 DeepSeek 空闲时段半价）。 「来源」列会标 reference:（内置）、channels:（可用渠道）、 plaza:（模型广场）或 imported:（从站导入），方便分辨数据从哪来。

导入的是哪个价？是站方自己标的模型原价（还没乘分组倍率的那一层）， 这样倍率才有意义。模型广场里另有一个叫「官方价」的字段，实测不少站把它填成同一个占位值 （比如所有 deepseek 模型都报 0.15），所以工具不用它。

页面底部还有汇率（USD→CNY）：只影响按美元标价的站点，人民币标价的站不受影响。

它是怎么工作的

整个工具是一条闭环：探针产生评分 → 评分决定路由 → 路由产生真实流量 → 流量回写评分。 下面拆开讲每一步在做什么、为什么这么做。

① 探针：查的是「有没有偷工」，不是「模型聪不聪明」

每次探测对一个模型发 5 个请求，分别对应中转站最常见的几种偷工方式。 它测的不是 MMLU 那种「模型有多聪明」——同一个模型在 A 站和 B 站能力本来就一样， 有差别的是它们有没有老实提供服务。

② 评分：两个维度分开算

可用率 = 成功次数 ÷ 总次数（探针 + 真实流量一起算）
完整性 = 指纹通过率 × 0.5 + 未截断率 × 0.3 + 计费正常率 × 0.2
质量 = 可用率 × 完整性
任一维度低于 0.8 就标记为不可用，不参与路由。

评分有有效期（默认 6 小时）。过期后它不再排在最前面，只作为兜底候选—— 因为一次真实调用本身就是证据：先派它跑一轮，下一轮评分就有新鲜数据了。 所以别把过期当成「不能用」，它只是「不再是首选」。定时探测是为了让评分保持新鲜。

③ 决策：先筛掉，再比价

准入门槛（硬约束，不登场）
· 慢速 —— 首字超过「慢速档位限制」，也就是你自己设的那条线
· 可疑 / 不稳定 —— 探针抓到掉包、截断、虚报，或真实可用率不到 80%
· 没有可信样本 —— 探针全被额度/限流挡住，可用率根本没有分母

能登场但只做兜底：评分过期、还没探测过。它们排在健康供给之后， 前面的都不行时才轮到——派过去的那次真实调用会顺手把它们的数据刷新。
有效成本排序 —— 能登场的按 价格 ÷ 质量 从小到大排。

全部候选都不登场时，网关直接报错，不会拿慢的或可疑的凑合： 只有慢速问题 → 报「上游速度慢于首字门槛」，其余情况 → 报「没有可用供给」， 错误体里逐站写明原因（error.type 分别是 upstream_too_slow 和 no_available_supply）。

慢速档位限制就在「智能决策」页顶部：点刻度条，或者填毫秒数。1000~20000ms 共 20 档， 按 500 为界就近取档（8600 按 9000、8499 按 8000）。每档带一个速度等级 （极快 / 快 / 正常 / 偏慢 / 慢），只是给人看的手感提示，判定永远比毫秒数。 留空 = 不限，那就是纯性价比模式。
「可疑 / 不稳定」这一条可以用探针页的 放行可疑供给 开关关掉，首字门槛不受那个开关影响。

为什么用除法而不是加权求和？因为「便宜 10% 但降智 30%」的站，加权后可能仍然胜出； 而除以质量之后，质量掉一半成本就翻倍，再怎么便宜也压不住。 这个公式还天然可解释：它表示「为一份可信输出实际付了多少钱」。

④ 路由：首选挂了会自动换下一个

这是网关的核心能力。同一个模型，如果排第一的站挂了，会自动试第二个、第三个， 客户端完全感知不到。关键在流式转发的边界： 必须读到第一个 chunk 并确认它不是错误，才向客户端提交响应头。

· 首字节之前失败 —— 静默换下一个站，客户端无感
· 首字节之后失败 —— 已经吐数据了，只能报错收尾，不能重试
所以顺序很重要：第一个站要选最可能成功的，这就是为什么要排除不可信和太慢的。

⑤ 回写：真实流量也算数

探针是模拟请求，测不出「高峰期 5xx」这类问题。所以网关每次转发的成败也会累计到对应站上， 和探针一起算可用率。一个站探针正常、但连续 3 次真实请求失败，可用率会掉到 63%， 状态自动变成「不稳定」，下次路由就跳过它。

几个刻意的取舍

延迟不参与加权排序 —— 延迟和价格量纲不同，硬凑成分数会失真。 改成一个可选上限：超过就不参与路由，规则简单可预期。
缓存命中率只展示、不折算成本 —— 缓存收益取决于你的使用模式。 前缀都不重复的话命中率就是 0，那个「便宜」对你没意义。
余额读不到就留空 —— 多数站不对 API Key 开放余额接口，工具不会猜一个数字填进去。

常见问题

余额读不到？ 多数站不对 API Key 开放余额接口。可以在站点卡片上点「令牌」填一个后台登录令牌， 或者直接手动填余额。
「导入倍率」和「基准价导入」有什么区别？ 站点页的导入倍率写的是倍率， 基准价页的写的是官方价。两边分工：官方价归基准价页，折扣归站点页。
为什么同一个模型在两个分组里价格不一样？ 正常。分组背后是不同的上游渠道， 原价和倍率都可能不同。所以必须先选对分组，价格才有意义。
选了分组，价格还是没变？ 两种情况：① 那个模型没有基准价，只能填绝对价， 提示里会写「N 个缺基准价」，去基准价页补上；② 这个模型不在你选的分组里，会算进「未匹配」。
能不能不选分组？ 能，会按站点原价（倍率 1）算。价格偏贵、不会偏便宜， 比价方向不会错，只是不如填准了精确。
为什么结果可疑？ 探针发现指纹不符、输出被截断或用量虚报。点探针页的行能看到原始返回证据。
一定要用网关吗？ 不一定。只用来比价和检测也完全够用。网关的额外价值是自动选站、 一个 Key 走全部站、按客户端统计用量。
多个实例能同时跑吗？ 不能。daemon 会用 daemon.lock 拒绝第二个实例，避免两边抢同一个数据目录。

数据存在哪

全部在本机 ~/.manage-api/，不联网、不上传。Key 加密存储，界面只显示尾号。 启动时和之后每天会自动备份到数据目录同级的 manage-api-backups/（含 master.key，默认留 30 份）。 恢复时 db.json 和 master.key 必须一起拷回；只恢复 db 会导致 Key 解不开。

ManageAPI solves one problem: you bought several AI relays but cannot tell which is cheaper, or which one is cutting corners. It puts them side by side, probes them on a schedule, then lets a local gateway pick a site for you. Everything runs on your machine — no data leaves it.

Quick start

  1. On Sites, add a relay (the base URL must end with /v1) and paste its key
  2. Click One-click sync: models, balance and group detection run in sequence; without a token group detection is skipped
  3. If no group was detected, click Import ratios and pick the group you actually bought
  4. For models without an official price, add one on Benchmarks, or load the built-in list
  5. Run a probe on the Probes page so the tool knows which sites to trust
  6. Routing picks a site automatically; you can override the order on Routing
  7. Copy the URL and key from Gateway into DSH or any OpenAI-compatible client
  8. The language switch sits in the top right; your choice is remembered

Each page

Overview

A summary you can open without filling anything in.
· Headline — which site is cheapest right now for the model you actually use, and by how much
· Four stats — sites, model supplies, comparable models, max price spread
· Needs attention — sites the probes flagged, grouped by site with the reason
· Sites at a glance — ranked by long-term score: green healthy, yellow watch, red unstable

Sites

Where you record relays and keys — and the monitor page too: balance curve, ratio changes and upstream announcements on top, site cards below. One site can hold several keys.
· Name — anything you like, only for your own reference
· Base URL — the API endpoint the relay gave you, it must end with /v1 (e.g. https://api.example.com/v1)
· Type — pick "Not sure" if you do not know; it changes nothing
· Key — paste the full sk-...; stored encrypted, only the last digits are shown

Each site card has a row of buttons:

· One-click sync — models → balance → (with a token) group detection, run in sequence; one failing step does not stop the others.
· Keys — expands this site's key list: add or remove keys, see the group bound to each.
· Group ratios — expands the ratio rows so you can edit a ratio or restore site values. See the Groups section.
· Import ratios — the manual path when detection fails: list the site's groups and pick one.
· Usage check — pulls the site's own recorded spend and compares it with our estimate.
· Export config — generates an OpenAI-compatible snippet you can paste into a client.
· Token (on the site card) — the site's login token, used to read balance, usage and groups. One token per backend account; never used for chat.
· Group (on the key row) — shows which group this key belongs to; click it to change.

Getting the token: log in to the site → F12 → Network → click any /api/v1/ request → copy the Authorization value from Request Headers (drop the Bearer prefix). Tokens expire in 7–30 days; copy a fresh one when they do.

Credit where it is due: the site-card layout (channel cards, group chips, toolbar) is inspired by bejix/upstream-ops. Only the layout is borrowed; data and interactions are implemented here.

Groups

A relay charges model base price × group ratio. A ratio of 0.1 means 90% off, 0.3 means 70% off.
A "group" is the tier you bought. One site often has a dozen of them — discount pool, Pro pool, enterprise channel, per-request billing, a dedicated expensive group for one model. The same model can differ several times over between groups.

Why you must pick it yourself? Which group you are in is a commercial fact, not something the API exposes. A key tells you which models you can call; it never says which tier it belongs to. The tool can list every group and ratio, but the last click has to be yours.

What happens after you click Import ratios:
① The site's groups appear, each with its ratio and how many of your models it covers; usable ones first
② You pick the one you bought and click Apply ratios
③ The group is stored on the key, ratios are written to every model below, and Pricing / Routing update
④ Next time the picker opens, it preselects the same group

Where the data comes from: with a token it reads /api/v1/channels/available (the richest source, no model plaza required); without one it falls back to the model plaza. If neither works it tells you why.

Reading the group ratio rows:
· From site (green) — matches what the site publishes, untouched
· Custom (amber) — you edited it; the site's original value is shown next to it
· Mixed — models in this group no longer share one ratio (some were edited individually)
· Editing the box sets a custom ratio for every model in that group
· When a Restore button appears, it goes back to the site value; "Restore all to site values" does the whole site

Custom ratios have a real use: if the site claims 0.15 but a usage check shows you are actually paying what 0.18 would cost, set 0.18 so the comparison stays honest.

Deleting a group: the trash icon on a group chip, the Delete button at the end of a group-ratio row, or the delete button in the Pricing table's group column. What happens depends on where the group came from:
· A group created by “+” on the Pricing page — no key backs it, so its model rows are deleted with it
· A group on a key — the key stays; only the group assignment is cleared. Click “Pick group” on that key to import the group again; its models and ratios come back (no manual sync needed)

Seeing what is inside a group: click a group chip on a site card (or the “N models” count in a group-ratio row) and a card pops up in the middle listing every model synced under that group with its effective price (ratio applied). Ignored models are listed and tagged “Ignored”; delisted ones are not shown. Press Esc or click the backdrop to close.

Free

Free relay models and free agent-platform credits live on their own page — not part of paid comparison and not part of automatic routing. The page has two tabs: relay free models and platform credits.

Relay free models: models whose effective price is 0. Fingerprint / truncation / quota / score expiry act as gates — anything that fails is excluded outright, so "cheap but bad" gets no slot.

Platform credits: free allowance from agent products such as WorkBuddy, CodeBuddy and ZCode.
· Connect — WorkBuddy / CodeBuddy authorise once and then read credits automatically. The endpoint belongs to the vendor's own IDE, so it is marked experimental: a platform update may break it, and a broken reader only means no numbers, nothing else.
· Check in — only platforms that implement automatic check-in show this button. It calls the real endpoint and only writes the ledger on success; clicking twice the same day counts once. Manual platforms and ZCode have no automatic check-in, so no button appears.
· Accounts — one platform can hold several accounts; switch the active one or delete an account from the card.
· Refresh / Diagnose — re-read the quota, or copy the platform's raw response when a field does not line up.
· Remaining means what is usable this cycle, not the plan's total; reset time and one-off bonus credits are reported separately.

The free pool is used only when you ask for it: point the client at http://127.0.0.1:4319/free/v1, or prefix a model with free/. When it runs dry it returns 402 — it never silently falls back to paid.

Pricing

The same model compared across sites.
· Search — filter by model name; the right side shows "N / M models"
· Cache — its own column: hit rate from the latest probe, "—" when never probed
· Mode — "Ratio / Price": decides how this row is priced
· Input / Output — in Price mode, type unit prices directly; saves on blur
· Ratio — in Ratio mode: price = benchmark × ratio, no unit price needed
· + — duplicates the row to price the same model in another plan (the group it creates has no key)
· Trash icon — deletes the group this row belongs to (the key stays and can re-import it)
· ¥/Mtok — blended cost: 25% input, 75% output (the weight is adjustable next to the FX box)
· Spread — how much more expensive than the cheapest

Mode is explicit: only the active mode's inputs are editable. Switching from Ratio to Price seeds the current effective price into the inputs, so the row does not turn "unpriced" and vanish.

Row markers: Cheapest is the lowest price for that model; Suspicious means the probes do not trust the site — the price is still shown but it is not recommended; Too slow means first-token latency exceeded your limit. Cache hit rate has its own column; the small text under blended cost is the off-peak price.

When a site has several groups, the same model appears on several rows, each tagged with its group. Use + at the end of a row to add another group for that model; delete it on the Sites page when you no longer need it.

Routing

See who routing would pick, and override it. One table per model:
· Highlighted row — the site that would be picked now
· Effective cost — price ÷ quality, lower wins
· ↑↓ — reorder the available candidates; takes effect immediately
· Back to auto — clears the manual order

Manual order only affects rows that are usable. Untrusted, too-slow or expired supplies sink to the bottom by default and cannot be dragged up — availability is a hard rule, not an opinion. If you do want suspicious sites to compete, turn on "Allow suspicious supplies" on the Probes page; their status then reads "allowed".

Probes

Checks whether a site is cutting corners. Probe a single model, or all of them.
· Fingerprint — demands an exact fixed output; anything else suggests the request was rerouted
· Truncation — asks it to count to 120; stopping early means the upstream lowered max_tokens
· Billing — prompt_tokens far beyond the actual prompt means inflated usage
· Cache — sends the same long prefix twice and checks how much the second one hit (two requests)
· Self-identification — asks "what model are you"; recorded, never scored. Models misreport themselves all the time, and penalising that produces too many false positives.

Click any row to expand it — you can see how the score was computed and the raw evidence from the last probe.

Settings at the top:

· Auto probe — runs in the background on an interval. Default 1 hour; can be turned off. With many models, set it longer — every probe costs a few tokens.
· Score TTL — a score older than this is discarded and no longer used for routing.
· TTFT limit — supplies slower than this are excluded from routing. 0 means no limit.
· Allow suspicious supplies — off by default. When off, sites the probes flagged (fingerprint mismatch / truncated / inflated / expired score) are only a last resort; when on, they compete on effective cost like everything else.

Know the trade-off before turning it on: suspicious sites still sort by price ÷ quality, so half the quality doubles the cost — only a large enough discount wins. But they can genuinely return swapped or truncated answers. Turn it on when saving money matters more; leave it off when trustworthy output does. The TTFT limit is separate and unaffected.

Gateway

One endpoint in front of every site; the client only needs one key.
· URL — http://127.0.0.1:4319/v1
· Key — sk-mapi-...; create one per client
· Monthly limit — optional token cap per key; returns 429 when exceeded
· Rotate — replace a leaked key without touching the other clients

Recent requests logs every routing decision: who was chosen, how many attempts, how long it took. Expand a row to see the full candidate order and the failure reasons.

Usage

· Range — 7 / 30 / 90 days
· Daily bars — bar height is total tokens; hover for that day's breakdown
· By key / model / site — three tables: who used it, on what, and where it actually ran

Only requests through the gateway are counted. Calls you make directly on a site, or from clients that do not use the gateway, are not included.

Benchmarks

What ratios convert against — essentially the official price. Three sources:
· Import official prices — pick a site and pull them. Uses a token to read available channels, otherwise the model plaza. Only fills gaps, never overwrites
· Use this site's prices — takes one site's existing prices as the baseline, for when you trust it
· Load built-in prices — a bundled list; prices change often, verify before relying on it

You can edit prices in the table. "Off-peak in / out" is for time-of-day pricing (DeepSeek is half price off-peak, for example). The Source column shows reference: (built-in), channels: (available channels), plaza: (model plaza) or imported:, so you can tell where a number came from.

Which price gets imported? The site's own model base price — the layer before the group ratio is applied — otherwise ratios would be meaningless. The model plaza also exposes a field called "official price", but in practice several sites fill it with one placeholder value for everything (e.g. every deepseek model reporting 0.15), so the tool ignores it.

At the bottom of this page there is a USD→CNY rate: it only affects sites priced in USD.

How it works

The whole tool is one loop: probes produce scores → scores drive routing → routing produces real traffic → traffic feeds back into the scores. Each step is explained below.

① Probes: detecting shortcuts, not measuring intelligence

Each probe sends five requests to a model, covering the most common ways a relay cuts corners. It is not an MMLU-style benchmark — the same model is equally capable everywhere; what differs is whether the site actually delivers it.

② Scoring: two dimensions, kept separate

Availability = successful probes ÷ all samples (probes and real traffic together)
Integrity = fingerprint pass rate × 0.5 + not-truncated rate × 0.3 + normal billing rate × 0.2
Quality = availability × integrity
Anything below 0.8 on either dimension is marked unusable and excluded from routing.

Scores expire (6 hours by default). An expired score is not used — stale data is more dangerous than no data, because it makes you think you already checked. Scheduled probing exists to keep scores fresh.

③ Decision: filter first, then compare price

Hard constraints — untrusted, too slow, expired: pushed to the back as a last resort.
Effective cost — the rest are sorted by price ÷ quality, ascending.

The "untrusted" part can be switched off with Allow suspicious supplies on the Probes page: they then compete on effective cost instead of being pushed back. The TTFT limit is separate and unaffected. The switch also changes what Pricing calls "cheapest" and what the Overview concludes, so recommendations and real routing always use the same rule.

Why divide instead of weighting? Because "10% cheaper but 30% dumber" can still win a weighted sum, while dividing by quality doubles the cost when quality halves — no discount can outrun that. The formula is also explainable: it is "what you actually pay for one trustworthy answer".

④ Routing: fall through to the next site

This is the gateway's core value. If the first site for a model is down, the second and third are tried automatically and the client never notices. The tricky part is the streaming boundary: the first chunk must be read and confirmed not to be an error before response headers are committed.

· Failure before the first byte — silently switch, the client sees nothing
· Failure after the first byte — data is already flowing; we can only end with an error, not retry
That is why order matters: the first site must be the most likely to succeed.

⑤ Feedback: real traffic counts too

Probes are synthetic and cannot detect "5xx at peak hours". So every forwarded request also counts toward that site's availability. A site with healthy probes but three consecutive real failures drops to 63% availability, turns "unstable", and is skipped on the next route.

Deliberate trade-offs

Latency does not participate in ranking — it does not share units with price, and fudging it into a score distorts things. Instead there is an optional ceiling: slower than this is excluded, simple and predictable.
Cache hit rate is shown, not priced in — the benefit depends on your usage. If your prefixes never repeat the hit rate is 0 and that "discount" means nothing to you.
Balance is left blank when unreadable — most sites do not expose balance to API keys; the tool will not guess a number.

FAQ

Balance cannot be read? Most sites do not expose a balance endpoint to API keys. Click "Token" on the key row and paste a site login token, or just type the balance in.
Import ratios vs. import official prices? The site page writes ratios; the Benchmarks page writes official prices. Prices belong to Benchmarks, discounts belong to the site page.
Why does the same model cost different amounts in two groups? That is normal. Groups sit on top of different upstream channels, so both the base price and the ratio can differ. Picking the right group is what makes the price meaningful.
I picked a group but the price did not change? Two cases: ① the model has no benchmark price, so only an absolute price can be filled (the toast says "N without benchmark"); ② the model is not in that group, so it counts as unmatched.
Can I skip picking a group? Yes, it falls back to the site's base price (ratio 1). That overstates the cost rather than understating it, so the comparison still points the right way.
Why is a result suspicious? The probe found a fingerprint mismatch, truncated output or inflated usage. Expand the row on the Probes page to see the raw response.
Do I have to use the gateway? No. Price comparison and probing work on their own. The gateway adds automatic site selection, one key for every site, and per-client usage.
Can I run two instances? No. The daemon refuses a second instance with daemon.lock, so two processes cannot share one data directory.

Where the data lives

Everything is in ~/.manage-api/ on your machine. Nothing is uploaded. Keys are stored encrypted and only their last digits are shown. On startup and every day, the daemon backs up the data into manage-api-backups/ next to it (including master.key; 30 copies kept by default). Restore db.json and master.key together; a db without its key cannot decrypt saved keys.
