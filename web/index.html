ManageAPI

个人专属API网关

概览

通知

ManageAPI 解决一个问题：你买了几个 AI 中转站，但不知道哪个更划算、哪个在偷工减料。 它把这些站放在一起比价、定期检测质量，然后用一个本地网关替你自动选站。 全部在本机运行，数据不出本机。

快速开始

  1. 站点 页添加中转站（地址结尾要带 /v1），粘贴它的 Key
  2. 点 一键同步：拉模型、读余额、识别分组一次跑完；没有站点登录态时跳过识别分组
  3. 同步没认出分组，就打开 分组倍率 面板点 重新读取，在分组列表里手动选你买的那个
  4. 缺官方价的模型，去 基准价 页补上，或者载入内置参考价
  5. 去 探针 页跑一次检测，让程序知道哪些站可信
  6. 程序会按评分体系自动决定用哪个站，也可以在 智能决策 页手动调整先后
  7. 去 网关 页复制地址和 Key，填进 DSH 等 agent 平台
  8. 界面右上角可以切换中英文，选择会记住

各页面怎么用

概览

打开就能看的总结页，不需要填任何东西。
· 一句话结论 —— 你在用的那个模型，现在哪家最便宜、省多少
· 四个指标 —— 站点数、模型供给数、可比较的模型数、最大价差
· 需要关注 —— 探针判定有问题的站，按站聚合，写明原因
· 站点排名 —— 按长期评分排序，绿点健康、黄点需关注、红点不稳定

顶栏的「刷新」是全站刷新：除了界面状态（/api/state），还会重拉概览的余额和真实花费 （绕过 60 秒缓存）、监控页数据，以及用量页当前所选区间的数据。15 秒自动轮询仍是轻量的，只拉状态。

站点

录入中转站和 Key 的地方，同时也是监控页：上方是余额概览、倍率变动和上游公告，下方是站点卡。 一个站可以挂多个 Key。
· 名称 —— 随便填，只用于你自己识别
· 地址 —— 中转站给你的 API 地址，结尾必须带 /v1 （如 https://api.example.com/v1）
· 类型 —— 不确定就选「不确定」，登录站点后会自动识别（one-api / new-api / Sub2API）
· Key —— 粘贴完整的 sk-...，加密存储，界面只显示尾号

每个站点卡片上有一排按钮：

· 账号登录 —— 用站点后台的账号密码登录，自动获取令牌并续期（过期自动重登，10 分钟冷却）。验证码 / 2FA 的站不支持，会明确告诉你
· 一键同步 —— 同步模型 → 读余额 →（有登录态时）识别分组，串着跑完；某一步失败不影响其他步骤。
· 密钥 —— 展开这个站的 Key 列表：加 Key、删 Key、看每把 Key 绑的分组。
· 分组倍率 —— 展开分组倍率，改倍率或恢复站点值；面板里的 重新读取 是读不到后台时的手动方案：从站点读分组列表，你选买的那一档。详见下面「分组」一节。
· 用量核对 —— 拉站方逐条用量明细，和网关记录做扣费核验：单价对不对、token 数是否吻合。
· 导出配置 —— 生成 OpenAI 兼容的配置片段，方便复制到客户端。
· 自动续期（在站点卡片上）—— 显示登录态的状态徽章（未登录 / 已过期 / 自动 / 不续期）和到期日，旁边是「立即续期」按钮（没有登录态时显示「账号登录」）。登录态用来读余额、账单和识别分组，不参与对话；之后由刷新令牌自动续期。
· 充值汇率（在站点卡片上）—— 充 1 元到账多少站点额度。1:1 充值的站填 1；充 ¥100 到账 $120 填 0.83。留空 = 按市场汇率折算。「实际消费」用它把站点账单换算成人民币。
· 分组（在 Key 那一行）—— 显示这把 Key 属于哪个分组，点它也能打开选分组。

登录态怎么来：点站点卡片上的 账号登录，用站点后台的账号密码登录； 站点开了验证码 / 2FA、账号密码连不上时，用 导入登录态，把浏览器里登录响应的 JSON 整体贴进来。 之后由刷新令牌自动续期，令牌过期不用你管。不会自动续期的站会在卡片上写明原因。

余额概览

站点页上方那张图，两种看法：
· 全部站点（默认）—— 折线是各站余额合计，柱子是各站花费堆叠（每站一色）
· 单站 —— 点下方胶囊只看某个站，折线与柱子都换成该站数据，纵轴自动缩放到该站量级

为什么不做多线？多个站的余额叠在一起时，小站的线会被压到贴地、互相穿插，五个站就糊成一片。 所以只画合计，需要看单站时点胶囊切换。没余额也没花费的站不会出现在胶囊里。

花费 · 今天 / 本周 / 本月 只显示一个数字：实际消费。 它直接读站点自己的账单（/api/v1/usage 逐条汇总），不是网关侧估算—— 实测上游约 26% 的 token 不返回 usage、cached_tokens 也不稳定， 估算值和真实账单能差 7~10 倍。读不到账单时显示「未采集」，并写明是哪一种原因：
· N 个站点登录态已失效，续上才读得到账单 —— 卡片上会给一个「全部续期」按钮， 逐个续完再重采一轮
· 还没有站点登录态：先到站点页「账号登录」
· 有站点没开账单接口，读不到就显示未采集
采集失败也不再静默：令牌过期 / 无权限会记成「账单：<原因>」并标记该站登录态失效。 监控默认每 30 分钟采集一轮，可在探针页附近设置里调间隔或关掉。

分组

中转站的计费公式是 模型原价 × 分组倍率。倍率 0.1 就是打一折，0.3 是三折。
「分组」就是你买的那一档——同一个站常常有十几个分组（特惠池、企业通道、按次计费、 某个模型专用的高价组），同一个模型在不同分组里价格能差好几倍。

为什么必须你自己选？因为「你在哪个分组」是商务事实，API 读不出来。 Key 只能告诉你「能调用哪些模型」，不会告诉你「属于哪一档套餐」。 工具能列出所有分组和倍率，但最后一步得你点。

在分组倍率面板点「重新读取」之后会发生什么：
① 列出该站所有分组，每个后面标着倍率和能覆盖你几个模型，能用的排在前面
② 你选中自己买的那个，点「应用倍率」
③ 这个分组会记在 Key 上，倍率写进下面所有模型，比价 / 决策 / 路由立刻同步
④ 下次再点「重新读取」，会默认选中上次那个

数据从哪来：有站点登录态时读 /api/v1/channels/available（数据最全， 不要求站开广场）；没有登录态则回落「模型广场」。两条路都不通会直接告诉你原因。

分组倍率那几行怎么看：
· 标 站点值（绿）—— 和站点公布的一致，没动过
· 标 自定义（黄）—— 你手改过，旁边会写出站点原本是多少
· 标 混合 —— 这个分组下的模型倍率不一致（单独改过某几个）
· 直接改那个输入框就是自定义倍率，改一次该分组下所有模型一起变
· 出现「恢复」按钮时点一下，回到站点公布的值；顶部「全部恢复为站点值」是整个站一起还原

自己调倍率有实际用处：比如站方标的 0.15 你觉得有水分，按「用量核对」算出来实际是 0.18， 就手动改成 0.18，比价结果才准。

分组只有一把尺子：Key 上写的那一个。
· 站点卡上的「N 个分组」按 Key 数，没有分组的 Key 显示「未分组」，不算一个分组
· 每行供给上还记着一个「落价分组」，是上次算钱时用的分组，只作为快照；两者不一致说明 你换过分组而旧行还没跟着走
· 站点页工具栏的 整理分组 就是这个用途：先给预览（多少条要迁移、多少条是重复行）， 确认之后一次性把供给挪到 Key 的分组，并把同站同模型的重复行合并成一条
· 换分组时会自动迁移该 Key 的所有行，之后再同步不会出现「同一模型两条在售」

胶囊上的倍率是怎么显示的：优先用行上的实际倍率；行上还没落价时用站点给这把 Key 配的倍率； 再没有就用站点公布的同名分组倍率（会注明「还没落到价格」）；都没有才显示「未落价」。 名字太长会截断，悬停看全名，倍率始终可见；整组免费的显示 ×0。

分组胶囊的颜色是怎么来的？按这个分组里模型的厂商聚合推断，不是给分组名分配颜色：
· 国产厂商（deepseek / glm / qwen / kimi / doubao / minimax 等）统一蓝色
· 海外主流各自一色：OpenAI 绿、Claude 橙、Gemini 黄
· 组内全部免费（倍率 0 或双零价）→ 紫色，和站点卡「免费 N」标记同款
· 混合了多家厂商、或者组里还没有模型 → 中性灰（不猜）
所以灰胶囊通常意味着这把 Key 还没同步过模型，跑一次「一键同步」就会上色。

免费

中转站的免费模型和 Agent 平台的免费积分，单独收在一页，不参与付费比价，也不参与自动选站。 页内分两栏：中转站免费模型 和 平台积分。

中转站免费模型：实际价为 0 的模型，按指纹 / 未截断 / 额度耗尽 / 评分过期做闸门， 质量不达标就整个排除，不给「便宜但烂」留位置。

平台积分：WorkBuddy / CodeBuddy / ZCode 这类 Agent 产品的免费额度。
· 连接 —— WorkBuddy / CodeBuddy 点「连接」授权后自动读积分。接口是平台给自家 IDE 用的， 标了「实验性」，平台升级后可能失效；失效只是读不到数据，不影响其他功能
· 签到 —— 只有实现了自动签到的平台才显示这个按钮；签到会真实请求平台接口，成功才写账本， 同一天重复点只算一次。手动平台和 ZCode 没有自动签到，不会显示这个按钮
· 账号 —— 一个平台可以挂多个账号，卡片上能切换活跃账号、删除账号
· 刷新 / 诊断 —— 重新读额度；字段对不上时，把平台原始返回复制出来定位
· 剩余 指本周期还能用多少，不是套餐总量；重置时间与一次性赠量分开写

免费池只有显式使用时才会被调用：地址换成 http://127.0.0.1:4319/free/v1， 或者模型名前缀 free/。免费池用尽返回 402，不会静默回落到付费。

比价

同一个模型在不同站的价格横向对比。
· 搜索框 —— 输入模型名过滤，右边显示「N / M 个模型」
· 缓存 —— 单独一列：最近一次探测的缓存命中率，没探过显示「—」
· 模式 —— 「倍率 / 价格」二选一，决定这一行按哪种方式计价
· 输入价 / 输出价 —— 「价格」模式下直接填单价，失焦即保存
· 倍率 —— 「倍率」模式下填：实际价 = 基准价 × 倍率，不用再填单价
· 「＋」 —— 按当前行复制一条，用来给同一个模型建新分组
· ¥/百万 token —— 综合成本，输入按 25%、输出按 75% 加权（权重可在左下角调）
· 价差 —— 比最便宜的贵多少百分比

模式是显式开关，只有当前模式的输入框可编辑。从「倍率」切到「价格」时，程序会把当前折算价 种进输入框，不会因为切模式让这条供给变成「未定价」而消失。

行里的标记：「最便宜」是该模型当前最低价；「可疑」是探针判定不可信的站， 价格照常显示但不参与推荐。 缓存命中率在单独的「缓存」列；综合成本下方的小字是空闲时段价。

一个站挂了多个分组时，同一个模型会出现在同一列的多行里，行内标着是哪个分组。 想给某个模型单独加一个分组，点行尾的 「＋」 复制一条再改。

智能决策

看路由会选谁，也能手动干预。每个模型一张表：
· 绿底行 —— 当前会选中的那个站
· 价格 —— 名义单价（输入/输出按你的使用比例混合，再按缓存命中折掉复用部分）
· 质量 —— 三行：质量值 / 可靠度 × 快慢 / 样本数。质量的高低直接决定有效成本
· 排序键 —— 当前档位下真正用来排序的数字，副行写它和上一条差多少
· 命中率 —— 缓存复用比例，副行标出处：实测（你真实请求逐单记账）、 实测·少（样本不足，已向全局通常水平收缩）、先验（还没有样本，先按 85% 估）
· 首字TTFS / 输出速度TPS —— 两列分开：TTFS 是等到第一个字的毫秒数，TPS 是每秒输出多少 token。 TTFS 的副行 +Nms 是同一轮里比最快的那条慢多少（已扣掉本机链路）
· ↑↓ —— 调整「可用」候选的先后，改完立即生效
· 恢复自动 —— 清掉手动顺序，回到按排序键排

第一行的按钮是「置顶」，不是 ↑↓。点一下 = 把当前排头顺序冻结成手动顺序（进入手动模式， 和以前手动调序一样），再点一次 = 取消置顶、清空手动顺序回到自动排序。其余行仍是 ↑↓。

表头上方有 按对话长度看：[短对话] [中等对话] [长对话] 分段控件，首字 TTFS 和输出速度 TPS 两列一起分档显示。它只影响你看到的数字，不影响选站——真实选站由后端按每个请求自己的 prompt 大小取档（短对话 < 60k、中等 60k–180k、长对话 ≥ 180k）。首字本来就随对话变长而变慢， 不分档拿短请求和长请求一起比，谁快谁慢全凭运气。

页面左上角是「决策侧重」三档，只改排序键，不改准入：
· 价格 —— 名义单价最低优先，质量只用来挡不合格的
· 性价比（默认）—— 有效成本 = 价格 ÷ 质量，越低越优先
· 质量 —— 先比质量，同质量再比价格
两种情况下，价格差在 5% 以内的几条会粘住上次成功的那个站（避免为了省几厘钱把上游前缀缓存换掉）。

手动顺序只影响「可用」的那几条。不可信、评分过期的站默认排在后面， 你拖不动它——可用性是硬判断，不能被手动覆盖。 如果你确实想让可疑的站参与竞争，去探针页打开「放行可疑供给」，它们会正常参与排序， 状态列会标出「已放行」。

探针

检测站有没有偷工。每个模型可以单独点「探测」，也可以点「探测全部」。
· 指纹 —— 要求精确输出固定内容，返回不对说明可能被掉包
· 截断 —— 要求数到 120，没数完说明上游压低了 max_tokens
· 计费 —— 扣掉同一次请求命中的缓存后，计费输入仍远超实际请求规模，说明多收钱
· 缓存 —— 同一段长前缀连发两次，看第二次命中多少（这一步要发 2 个请求）
· 身份自述 —— 问它「你是什么模型」，结果只记录、不评分。 因为模型自述本来就不可信，同一个模型换个说法很常见，拿它扣分误伤太多。

点表格里任意一行会展开，能看到质量是怎么算出来的，以及最近一次探测的原始返回证据。

顶部设置项：

· 自动探测 —— 设间隔后后台定时跑。默认 1 小时，可以关掉。模型多的话建议设长一点， 每次探测都要花一点 token。
· 评分有效期 —— 超过这个时间没重新探测，评分就作废、不再参与路由。
· 首字与速度 —— 不再设固定上限：快慢按「同模型、同对话长度档的通常水平」折算成快慢分， 慢的站按比例降权、快的站加分，不会被直接踢出候选。
· 放行可疑供给 —— 默认关闭。关闭时，探针判定可疑（指纹不符 / 截断 / 虚报 / 评分过期）的站 只会排在最后兜底；打开后它们按有效成本正常参与竞争。

打开这个开关要清楚代价：可疑的站仍然按「价格 ÷ 质量」排序——质量差一半，成本就翻倍， 所以只有便宜到足够多才会被选中。但它确实可能给你返回掉包或截断的结果。 省钱优先就打开，输出可信优先就关着。快慢不受这个开关影响，它只看首字和输出速度。

网关

一个地址接管所有站，客户端只填一个 Key。
· 地址 —— http://127.0.0.1:4319/v1
· Key —— sk-mapi-...，点「新建 Key」可以给每个客户端建一把
· 月限额 —— 建 Key 时可设月度 token 上限，超了返回 429
· 轮换 —— 某把 Key 泄露了单独换，不影响其他客户端

最近请求表记录每次路由：选了谁、试了几次、耗时多少。 点开能看到完整的候选排序和失败原因。结果列有三种：
· 成功 —— 正常跑完
· 已交付 · 客户端先关 —— 上游已经把整轮发完（收到了 finish_reason 和 usage， 内容是完整的、token 账也是全的），是客户端（比如 DSH）拿到工具调用就主动断了、没等最后的 [DONE]。 它算成功，不拉低可用率
· 红字失败原因 —— 真的没拿到完整结果，按失败计

用量

· 范围 —— 7 / 30 / 90 天切换
· 按天柱图 —— 柱高是 token 总量，悬停看当天明细
· 按 Key / 模型 / 站点 —— 三张表，看谁用的、用的什么、实际跑在哪家

只有经过网关的请求才计入。如果你在站上直接用，或别的客户端没走网关，那些不会算进来。

基准价

倍率换算的参照物，本质就是「官方价」：实际价 = 基准价 × 倍率。 某个模型没有基准价，它的倍率就没法换算成钱，只能填绝对价。三个来源：
· 从站点导入官方价 —— 选一个站，一键拉取。有站点登录态读可用渠道、没有登录态读模型广场。 只补空缺，不覆盖你已有的
· 以此站已填价为准 —— 把某个站已经填好的实际价整体设为基准，适合你确信它没虚标
· 载入内置参考价 —— 工具内置的一份官方价，价格常变，务必核对

基准价存的是「站点原价」，不是打折后的价格。倍率行算钱时是 基准价 × 倍率， 如果基准价里已经含过一次倍率，就会打两次折（实测能差 12 倍）。历史上从广场 / 供应商导入的条目 曾经是折后价，所以工具栏有一个 校准为原价：按各站现在公布的原价重算受影响的条目， 先给预览再落库，手填和内置参考价不动。

币种不在这里选：基准价的币种跟着「站点卡片上的报价币种」走。行内只有在「手填、且没有站点 引用它」时才给下拉；跟站点声明冲突的行会标出来，去点「校准为原价」就按站点声明批量写回。 站点还没声明报价币种时，从它导入会被拒绝——先去站点卡片选 USD 或 CNY，否则基准价会按美元写， 人民币站会差一个汇率。

表格里可以直接改价格。「空闲输入 / 空闲输出」是峰谷定价用的（比如 DeepSeek 空闲时段半价）。 也可以点 ＋ 新增基准价 手动补一条（币种必选）。 「来源」列会标 reference:（内置）、channels:（可用渠道）、 plaza:（模型广场）或 imported:（从站导入），方便分辨数据从哪来。

导入的是哪个价？是站方自己标的模型原价（还没乘分组倍率的那一层）， 这样倍率才有意义。模型广场里另有一个叫「官方价」的字段，实测不少站把它填成同一个占位值 （比如所有 deepseek 模型都报 0.15），所以工具不用它。

页面底部还有汇率（USD→CNY）：只影响按美元标价的站点，人民币标价的站不受影响。

它是怎么工作的

整个工具是一条闭环：探针产生评分 → 评分决定路由 → 路由产生真实流量 → 流量回写评分。 下面拆开讲每一步在做什么、为什么这么做。

① 探针：查的是「有没有偷工」，不是「模型聪不聪明」

每次探测对一个模型发 5 个请求，分别对应中转站最常见的几种偷工方式。 它测的不是 MMLU 那种「模型有多聪明」——同一个模型在 A 站和 B 站能力本来就一样， 有差别的是它们有没有老实提供服务。

② 评分：两个维度分开算

可用率 = 成功次数 ÷ 总次数（探针 + 真实流量一起算）
完整性 = 指纹通过率 × 0.5 + 未截断率 × 0.3 + 计费正常率 × 0.2（只算测到的项，权重按剩余项归一）
可靠度 = 可用率 × 完整性
快慢 = 首字分0.6 × 速度分0.4
质量 = 可靠度 × 快慢

快慢的尺子是「同一个模型、同一档对话长度在售的全部供给」，不是固定毫秒：
· 首字分 = 通常水平首字 ÷ 本站首字，速度分 = 本站输出速度 ÷ 通常水平速度； 1.00 = 这个模型这一档的通常水平
· 真实速度按对话长度分三档：短对话（prompt < 60k）、中等对话（60k–180k）、 长对话（≥ 180k），每档各自取通常水平。比价 / 决策时用本次请求自己的档当尺子
· 取不到同档样本就标「未同档」，不给超额（快慢上限 1.00）——不拿短请求的快去担保长请求
· 样本少于 3 条时，偏差按比例向 1.00 收缩：1 条样本最多只能拉动 1/3
· 有真实流量样本的站按实测折算；只有探针数据的站走探针档，上限压到 1.00 （探针发的是 45 token 的小请求和 14.5k 的缓存探测，只能证明「不慢」，证明不了「更快」）
· 一项都没测到的，按 1.00（通常水平）算，不是按 0 罚

可靠度低于 0.8 就标记为不可用，不参与路由。快慢不影响准入——慢的站不会因为慢被踢出去， 只是有效成本被除得更高，自然排在后面。

评分有有效期（默认 6 小时）。过期后不再参与路由——过期数据比没有数据更危险， 因为它会让你误以为已经检查过了。定时探测就是为了让评分保持新鲜。

③ 决策：先筛掉，再比价

硬约束 —— 不可信、评分过期的，默认排到最后只做兜底。
有效成本排序 —— 剩下的按 价格 ÷ 质量 从小到大排。

这里的「价格」不是网站标的名义单价，而是按你的真实用法折算过的期望成本：
· 输入占比 —— 默认读你自己的真实流量（输入 token ÷ 全部 token），没有样本时按 90%
· 缓存折扣 —— 输入价按 1 − 命中率 × 0.9 折算。命中率是网关逐单记账算出来的： 缓存读 ÷ (净值 + 缓存读 + 缓存写)，并剔掉冷启动那几单（新会话、对话刚变、隔太久没用）
· 样本不足时会向全局通常水平收缩，避免一两单极端值决定排名

「不可信」这一条是可以用探针页的 放行可疑供给 开关关掉的：打开后它们不再被压到后面， 而是和健康的站一起按有效成本竞争。快慢（首字与输出速度）只通过质量折算进有效成本，不受这个开关影响。 注意开关会同时影响比价页的「最便宜」和概览页的结论，保证推荐和实际路由是同一套口径。

为什么用除法而不是加权求和？因为「便宜 10% 但降智 30%」的站，加权后可能仍然胜出； 而除以质量之后，质量掉一半成本就翻倍，再怎么便宜也压不住。 这个公式还天然可解释：它表示「为一份可信输出实际付了多少钱」。

④ 路由：首选挂了会自动换下一个

这是网关的核心能力。同一个模型，如果排第一的站挂了，会自动试第二个、第三个， 客户端完全感知不到。关键在流式转发的边界： 必须读到第一个 chunk 并确认它不是错误，才向客户端提交响应头。

· 首字节之前失败 —— 静默换下一个站，客户端无感
· 首字节之后失败 —— 已经吐数据了，只能报错收尾，不能重试
所以顺序很重要：第一个站要选最可能成功的，这就是为什么要排除不可信的。

⑤ 回写：真实流量也算数

探针是模拟请求，测不出「高峰期 5xx」这类问题。所以网关每次转发的成败也会累计到对应站上， 和探针一起算可用率。一个站探针正常、但连续 3 次真实请求失败，可用率会掉到 63%， 状态自动变成「不稳定」，下次路由就跳过它。

客户端提前断流、但上游已经把整轮交付完的请求（收到了 finish_reason 和 usage） 也记为有效样本——长对话几乎全是这种收尾方式，DSH 这类客户端拿到工具调用就断，不等最后的 [DONE]。它们在「最近请求」里显示为「已交付 · 客户端先关」，算成功，不拉低可用率。

网关还会对成功的真实响应做两类客观质量抽样：空回答（200 成功、正常结束却一个字都没有） 和计费异常（扣掉同一次请求命中的缓存之后，计费输入仍超过请求体估算的 4 倍）。 指纹和截断需要受控 prompt，真实请求里验不了——那两项只有探针能做。 站点把长系统提示算进 prompt 是常态，只要每次命中缓存，那部分几乎不花钱；所以判据只看「扣掉命中之后还剩下多少」。 抽样要攒够 5 个样本、异常率超过 20% 才影响评分，不足就只记录。

⑥ 采集：余额、账单、倍率、公告

比价和探针回答「现在哪家划算」，采集回答「这几天发生了什么」。默认每 30 分钟一轮（可关）。 采集只读站点接口、不花 token，所以能比探针勤。一个站一轮采四样，各自独立失败：
· 余额 —— 站点后台接口，需要站点登录态；读不到就显示「无数据」，不猜数字
· 实际消费 —— 站点自己的按天账单，见上面「余额概览」
· 分组倍率 —— /api/v1/channels/available，顺便把模型原价读回来
· 上游公告 —— 按标题 + 发布时间去重

遇到 401/403 会自己续一次：定时采集碰上登录态过期，会先自动续期，再重拉这一轮的账单， 不用你手动处理。续不上（登录态彻底失效）才记成「账单：<原因>」，并把该站标为登录态失效。

告警按「站点 × 类型」冷却：同样的余额过低六小时内只记一条，不然第一次接站就会被刷屏。 第一次采集只记基线、不发变动——否则一接入就是满屏「新出现」，那不是变动，那是初始状态。 余额告警阈值在设置里按美元填（人民币站按汇率折算后比），填 0 关闭。

几个刻意的取舍

延迟折成相对分，不做绝对门槛 —— 首字和速度不与价格相加，而是除以同模型同档对话的通常水平折成快慢分， 再乘进质量；绝对值（比如「3 秒」「15 秒」）受本机链路和请求长度影响太大，固定阈值只会误杀。
缓存命中率按你的实测折价，且只折输入侧 —— 命中率来自你自己的逐单记账， 所以它反映的正是你的用法；对话都不重复时命中率就是 0，折扣自动消失。
余额读不到就留空 —— 多数站不对 API Key 开放余额接口，工具不会猜一个数字填进去。

常见问题

余额读不到？ 多数站不对 API Key 开放余额接口。可以在站点卡片上点「账号登录」（或「导入登录态」）， 再不行就手动填余额。
花费显示「未采集」？ 「实际消费」只认站点自己的账单（/api/v1/usage）。 卡片上会写明是哪一种：还没有站点登录态、登录态已失效、或这个站没有开放账单接口。 工具不会拿估算冒充当账单。
花费比我预期的小？ 账单只统计经过这个站、且站点自己记了账的部分。 如果你在别的客户端直连这个站，那部分不在本工具的采集范围内；反过来， 网关侧估算缺约 26% 的 token，所以我们也绝不用估算来当花费。
分组胶囊是灰的？ 颜色按组内模型的厂商聚合推断：单厂商上色，混合厂商或组内还没有模型是灰色。 灰的通常意味着这把 Key 还没同步过模型，跑一次「一键同步」就好。
令牌过期了要重新抓吗？ 不用。用「账号登录」或「导入登录态」接上的站会自动续期（遇到 401/403 续一次， 10 分钟冷却）；不会自动续期的站会在卡片上写明原因，重新登录一次即可。
「重新读取」和「基准价导入」有什么区别？ 站点页分组倍率面板的「重新读取」写的是倍率， 基准价页的写的是官方价。两边分工：官方价归基准价页，折扣归站点页。
为什么同一个模型在两个分组里价格不一样？ 正常。分组背后是不同的上游渠道， 原价和倍率都可能不同。所以必须先选对分组，价格才有意义。
选了分组，价格还是没变？ 两种情况：① 那个模型没有基准价，只能填绝对价， 提示里会写「N 个缺基准价」，去基准价页补上；② 这个模型不在你选的分组里，会算进「未匹配」。
能不能不选分组？ 能，会按站点原价（倍率 1）算。价格偏贵、不会偏便宜， 比价方向不会错，只是不如填准了精确。
为什么结果可疑？ 探针发现指纹不符、输出被截断或用量虚报。点探针页的行能看到原始返回证据。
一定要用网关吗？ 不一定。只用来比价和检测也完全够用。网关的额外价值是自动选站、 一个 Key 走全部站、按客户端统计用量。
多个实例能同时跑吗？ 不能。daemon 会用 daemon.lock 拒绝第二个实例，避免两边抢同一个数据目录。

数据存在哪

全部在本机 ~/.manage-api/，不联网、不上传。Key 加密存储，界面只显示尾号。 启动时和之后每天会自动备份到数据目录同级的 manage-api-backups/（含 master.key，默认留 30 份）。 恢复时 db.json 和 master.key 必须一起拷回；只恢复 db 会导致 Key 解不开。

ManageAPI solves one problem: you bought several AI relays but cannot tell which is cheaper, or which one is cutting corners. It puts them side by side, probes them on a schedule, then lets a local gateway pick a site for you. Everything runs on your machine — no data leaves it.

Quick start

  1. On Sites, add a relay (the base URL must end with /v1) and paste its key
  2. Click One-click sync: models, balance and group detection run in sequence; without a login session group detection is skipped
  3. If no group was detected, open the Group ratios panel, click Reload and pick the group you actually bought
  4. For models without an official price, add one on Benchmarks, or load the built-in list
  5. Run a probe on the Probes page so the tool knows which sites to trust
  6. Routing picks a site automatically; you can override the order on Routing
  7. Copy the URL and key from Gateway into DSH or any OpenAI-compatible client
  8. The language switch sits in the top right; your choice is remembered

Each page

Overview

A summary you can open without filling anything in.
· Headline — which site is cheapest right now for the model you actually use, and by how much
· Four stats — sites, model supplies, comparable models, max price spread
· Needs attention — sites the probes flagged, grouped by site with the reason
· Sites at a glance — ranked by long-term score: green healthy, yellow watch, red unstable

The refresh button in the top bar reloads everything: besides the UI state (/api/state), it refetches the overview's balance and actual spend (bypassing the 60-second cache), the monitor data, and the usage page for the range you have selected. The 15-second auto-poll stays lightweight — state only.

Sites

Where you record relays and keys — and the monitor page too: balance overview, ratio changes and upstream announcements on top, site cards below. One site can hold several keys.
· Name — anything you like, only for your own reference
· Base URL — the API endpoint the relay gave you, it must end with /v1 (e.g. https://api.example.com/v1)
· Type — pick "Not sure" if you do not know; an account login detects it automatically (one-api / new-api / Sub2API)
· Key — paste the full sk-...; stored encrypted, only the last digits are shown

Each site card has a row of buttons:

· Account login — sign in with the site's dashboard credentials; the token is fetched and renewed automatically (on 401, with a 10-minute cooldown). Sites with captcha / 2FA are not supported and say so.
· One-click sync — models → balance → (with a login session) group detection, run in sequence; one failing step does not stop the others.
· Keys — expands this site's key list: add or remove keys, see the group bound to each.
· Group ratios — expands the ratio rows so you can edit a ratio or restore site values. The Reload button inside it is the manual path when detection fails: it reads the site's group list and you pick the tier you bought. See the Groups section.
· Usage check — pulls the site's per-request usage records for a billing audit: are the unit prices right, do the token counts line up.
· Export config — generates an OpenAI-compatible snippet you can paste into a client.
· Auto-renew (on the site card) — shows a login-state badge (not signed in / expired / automatic / no renewal) and the expiry date, next to an Renew now button (it reads Account login when there is no session). The session is used to read balance, bills and groups; never for chat. After that the refresh token renews it automatically — sites that cannot renew state the reason on the card.
· Top-up rate (on the site card) — how much site credit one unit of real money buys. Fill 1 for 1:1 top-ups; if ¥100 buys $120 of credit, fill 0.83. Empty = use the market FX rate. "Actual spend" uses it to convert the site's bill into your currency.
· Group (on the key row) — shows which group this key belongs to; click it to change.

Where the login session comes from: click Account login on the site card and sign in with the site's dashboard credentials. If the site has a captcha / 2FA or the password does not go through, use Import session and paste the login response JSON from the browser. After that the refresh token renews it automatically — an expired token is no longer your problem. Sites that cannot auto-renew say why on the card.

Balance overview

The chart at the top of Sites has two views:
· All sites (default) — the line is total balance across sites, the bars are per-site spend, stacked (one colour each)
· Single site — click a chip below to focus one site; both line and bars switch to it and the axis rescales to that site's magnitude

Why not multiple lines? Overlay several sites and the small ones flatten against the floor and cross each other — five sites already smear into one band. So only the total is drawn; switch chips to inspect one. Sites with neither balance nor spend are not listed.

Spend · today / week / month shows one number: actual spend. It is read straight from the site's own bill (/api/v1/usage, summed per request), not estimated by the gateway — about 26% of upstream tokens arrive without usage and cached_tokens is unstable, which puts estimates anywhere from 7× to 10× off. When the bill cannot be read it says not collected and names the reason:
· {n} site session(s) expired — bills only come back once they are renewed — the card then offers a Renew all button that renews each one and re-collects
· No site session yet: sign in from the Sites page first
· Some sites expose no billing API; those stay uncaptured
Collection failures are no longer silent: an expired token / no permission is recorded as "bill: <reason>" and the site is marked session-invalid. Collection runs every 30 minutes by default and can be changed or turned off in settings.

Groups

A relay charges model base price × group ratio. A ratio of 0.1 means 90% off, 0.3 means 70% off.
A "group" is the tier you bought. One site often has a dozen of them — discount pool, Pro pool, enterprise channel, per-request billing, a dedicated expensive group for one model. The same model can differ several times over between groups.

Why you must pick it yourself? Which group you are in is a commercial fact, not something the API exposes. A key tells you which models you can call; it never says which tier it belongs to. The tool can list every group and ratio, but the last click has to be yours.

What happens after you click Reload in the Group ratios panel:
① It lists the site's groups, each with its ratio and how many of your models it covers; usable ones first
② You pick the one you bought and click Apply ratios
③ The group is stored on the key, ratios are written to every model below, and Pricing / Routing update
④ Next time you click Reload, it preselects the same group

A group lives on the key — that is the single source of truth.
· "N groups" on a site card counts keys; a key without a group reads "no group" and is not counted
· Each supply row also carries the group used for its last pricing, as a snapshot. If the two differ, you changed the group and the old rows have not followed yet
· Tidy groups on the site toolbar does exactly that: first a preview (how many rows move, how many are duplicates), then one confirmed pass that moves rows onto the key's group and merges duplicates of the same model into one
· Changing a group migrates that key's rows automatically, so the next sync never creates a second live row for the same model

How the chip gets its ratio: the row's actual ratio first; if the row has not been priced yet, the ratio the site assigned to this key; then the site's published ratio for a same-named group (marked "not priced yet"); only if none exist, "not priced". Long names are truncated with the full name on hover and the ratio always visible; fully free groups read ×0.

Where the data comes from: with a site login session it reads /api/v1/channels/available (the richest source, no model plaza required); without one it falls back to the model plaza. If neither works it tells you why.

Reading the group ratio rows:
· From site (green) — matches what the site publishes, untouched
· Custom (amber) — you edited it; the site's original value is shown next to it
· Mixed — models in this group no longer share one ratio (some were edited individually)
· Editing the box sets a custom ratio for every model in that group
· When a Restore button appears, it goes back to the site value; "Restore all to site values" does the whole site

Custom ratios have a real use: if the site claims 0.15 but a usage check shows you are actually paying what 0.18 would cost, set 0.18 so the comparison stays honest.

Where do the chip colours come from? They are inferred from the vendors of the models in that group, not assigned to group names:
· Domestic vendors (deepseek / glm / qwen / kimi / doubao / minimax …) share blue
· Major overseas vendors each get a colour: OpenAI green, Claude orange, Gemini yellow
· Every model in the group is free (ratio 0 or both prices 0) → purple, same as the "free N" badge
· Mixed vendors, or the group has no models yet → neutral grey (no guessing)
A grey chip usually means that key has not synced models yet — run One-click sync and it colours in.

Free

Free relay models and free agent-platform credits live on their own page — not part of paid comparison and not part of automatic routing. The page has two tabs: relay free models and platform credits.

Relay free models: models whose effective price is 0. Fingerprint / truncation / quota / score expiry act as gates — anything that fails is excluded outright, so "cheap but bad" gets no slot.

Platform credits: free allowance from agent products such as WorkBuddy, CodeBuddy and ZCode.
· Connect — WorkBuddy / CodeBuddy authorise once and then read credits automatically. The endpoint belongs to the vendor's own IDE, so it is marked experimental: a platform update may break it, and a broken reader only means no numbers, nothing else.
· Check in — only platforms that implement automatic check-in show this button. It calls the real endpoint and only writes the ledger on success; clicking twice the same day counts once. Manual platforms and ZCode have no automatic check-in, so no button appears.
· Accounts — one platform can hold several accounts; switch the active one or delete an account from the card.
· Refresh / Diagnose — re-read the quota, or copy the platform's raw response when a field does not line up.
· Remaining means what is usable this cycle, not the plan's total; reset time and one-off bonus credits are reported separately.

The free pool is used only when you ask for it: point the client at http://127.0.0.1:4319/free/v1, or prefix a model with free/. When it runs dry it returns 402 — it never silently falls back to paid.

Pricing

The same model compared across sites.
· Search — filter by model name; the right side shows "N / M models"
· Cache — its own column: hit rate from the latest probe, "—" when never probed
· Mode — "Ratio / Price": decides how this row is priced
· Input / Output — in Price mode, type unit prices directly; saves on blur
· Ratio — in Ratio mode: price = benchmark × ratio, no unit price needed
· + — duplicates the row, for giving one model a second group
· ¥/Mtok — blended cost: 25% input, 75% output (the weight is adjustable next to the FX box)
· Spread — how much more expensive than the cheapest

Mode is explicit: only the active mode's inputs are editable. Switching from Ratio to Price seeds the current effective price into the inputs, so the row does not turn "unpriced" and vanish.

Row markers: Cheapest is the lowest price for that model; Suspicious means the probes do not trust the site — the price is still shown but it is not recommended. Cache hit rate has its own column; the small text under blended cost is the off-peak price.

When a site has several groups, the same model appears on several rows, each tagged with its group. Use + at the end of a row to add another group for that model.

Routing

See who routing would pick, and override it. One table per model:
· Highlighted row — the site that would be picked now
· Price — nominal unit price, blended by your input/output mix and discounted by cache reuse
· Quality — three lines: the value / reliability × speed score / sample count
· Sort key — the number actually used to rank in the current mode; the sub-line says how far it is from the row above
· Hit rate — cache reuse ratio; the sub-line names the source: measured (your own per-request ledger), measured·few (too few samples, shrunk towards the usual level), prior (no samples yet, starts at 85%)
· First token (TTFS) / Output speed (TPS) — two separate columns: TTFS is the milliseconds until the first token, TPS is how many tokens per second. The +Nms sub-line of TTFS is how much slower than the fastest of the same probe round, with local link latency subtracted
· ↑↓ — reorder the available candidates; takes effect immediately
· Back to auto — clears the manual order

The first row's button is "Pin", not ↑↓. Click once = freeze the current top order into a manual order (manual mode, same as manual reordering); click again = unpin, clear the manual order and go back to automatic ranking. Other rows keep ↑↓.

Above the headers sits a View by chat length: [short chat] [medium chat] [long chat] segment control that buckets both the TTFS and TPS columns. It only changes the numbers you see, never which site is picked — the backend buckets every request by its own prompt size (short < 60k, medium 60k–180k, long ≥ 180k). First-token latency grows with chat length anyway; compare short and long prompts together and the winner is whoever got the luckier draw.

Routing preference at the top left has three modes. It only changes the sort key, never admission:
· Price — lowest nominal price first; quality only filters out failures
· Value (default) — effective cost = price ÷ quality, lowest first
· Quality — highest quality first, price breaks ties
In all modes, supplies within 5% of each other stay on the site that last succeeded, so a few pennies never throw away the upstream prompt cache.

Manual order only affects rows that are usable. Untrusted or expired supplies sink to the bottom by default and cannot be dragged up — availability is a hard rule, not an opinion. If you do want suspicious sites to compete, turn on "Allow suspicious supplies" on the Probes page; their status then reads "allowed". Speed never gates admission — it is folded into quality.

Probes

Checks whether a site is cutting corners. Probe a single model, or all of them.
· Fingerprint — demands an exact fixed output; anything else suggests the request was rerouted
· Truncation — asks it to count to 120; stopping early means the upstream lowered max_tokens
· Billing — billed input, after subtracting the cache hits of the same request, far beyond the actual prompt means you are being overcharged
· Cache — sends the same long prompt twice and checks how much the second one hit (two requests)
· Self-identification — asks "what model are you"; recorded, never scored. Models misreport themselves all the time, and penalising that produces too many false positives.

Click any row to expand it — you can see how the score was computed and the raw evidence from the last probe.

Settings at the top:

· Auto probe — runs in the background on an interval. Default 1 hour; can be turned off. With many models, set it longer — every probe costs a few tokens.
· Score TTL — a score older than this is discarded and no longer used for routing.
· Speed — there is no fixed ceiling any more: speed is scored against the usual level of the same model and chat-length tier, so a slow supply loses cost efficiency instead of being excluded.
· Allow suspicious supplies — off by default. When off, sites the probes flagged (fingerprint mismatch / truncated / billing anomaly / expired score) are only a last resort; when on, they compete on effective cost like everything else.

Know the trade-off before turning it on: suspicious sites still sort by price ÷ quality, so half the quality doubles the cost — only a large enough discount wins. But they can genuinely return swapped or truncated answers. Turn it on when saving money matters more; leave it off when trustworthy output does. Speed is not a gate any more: it is folded into the speed score.

Gateway

One endpoint in front of every site; the client only needs one key.
· URL — http://127.0.0.1:4319/v1
· Key — sk-mapi-...; create one per client
· Monthly limit — optional token cap per key; returns 429 when exceeded
· Rotate — replace a leaked key without touching the other clients

Recent requests logs every routing decision: who was chosen, how many attempts, how long it took. Expand a row to see the full candidate order and the failure reasons. The result column has three states:
· success — ran to completion normally
· delivered · client hung up first — the upstream already sent the whole turn (it received finish_reason and usage, so the content and the token accounting are complete); the client (DSH, for instance) hung up after the tool call without waiting for the final [DONE]. It counts as a success and does not lower availability
· a red failure reason — the turn really did not arrive complete, counted as a failure

Usage

· Range — 7 / 30 / 90 days
· Daily bars — bar height is total tokens; hover for that day's breakdown
· By key / model / site — three tables: who used it, on what, and where it actually ran

Only requests through the gateway are counted. Calls you make directly on a site, or from clients that do not use the gateway, are not included.

Benchmarks

What ratios convert against — essentially the official price. Three sources:
· Import official prices — pick a site and pull them. With a site login session it reads available channels, otherwise the model plaza. Only fills gaps, never overwrites
· Use this site's prices — takes one site's existing prices as the baseline, for when you trust it
· Load built-in prices — a bundled list; prices change often, verify before relying on it

You can edit prices in the table. "Off-peak in / out" is for time-of-day pricing (DeepSeek is half price off-peak, for example). The Source column shows reference: (built-in), channels: (available channels), plaza: (model plaza) or imported:, so you can tell where a number came from.

Which price gets imported? The site's own model base price — the layer before the group ratio is applied — otherwise ratios would be meaningless. Older imports stored the already-discounted number, so the toolbar has Calibrate to base prices: it recomputes the affected entries from each site's current published base price, shows a preview first, and leaves hand-filled and built-in entries untouched. The model plaza also exposes a field called "official price", but in practice several sites fill it with one placeholder value for everything (e.g. every deepseek model reporting 0.15), so the tool ignores it.

Currency is not chosen here: a benchmark entry follows the price currency on the site card. The inline currency picker only appears for hand-filled entries that no site references; entries that disagree with a site's declaration are flagged, and Calibrate to base prices writes them back. Importing from a site that has not declared its price currency is refused — set USD or CNY on the site card first, otherwise base prices land as USD and a CNY site will be off by a whole exchange rate.

At the bottom of this page there is a USD→CNY rate: it only affects sites priced in USD. You can also add an entry manually with + Add benchmark price (currency required).

How it works

The whole tool is one loop: probes produce scores → scores drive routing → routing produces real traffic → traffic feeds back into the scores. Each step is explained below.

① Probes: detecting shortcuts, not measuring intelligence

Each probe sends five requests to a model, covering the most common ways a relay cuts corners. It is not an MMLU-style benchmark — the same model is equally capable everywhere; what differs is whether the site actually delivers it.

② Scoring: two dimensions, kept separate

Availability = successful probes ÷ all samples (probes and real traffic together)
Integrity = fingerprint pass rate × 0.5 + not-truncated rate × 0.3 + normal billing rate × 0.2 (only measured items count; weights renormalise over the rest)
Reliability = availability × integrity
Speed score = TTFT score0.6 × throughput score0.4
Quality = reliability × speed score

The speed ruler is every on-sale supply of the same model in the same chat-length tier, not a fixed number of milliseconds:
· TTFT score = usual-level TTFT ÷ this site's TTFT; throughput score = this site's tok/s ÷ usual-level tok/s. 1.00 is the usual level of that model in that tier
· Real speed is bucketed by chat length: short (prompt < 60k), medium (60k–180k), long (≥ 180k); each tier has its own usual level. Comparison and routing use the tier of the request itself as the ruler
· With no sample in the same tier it is marked "size not matched" and no bonus is granted (speed score capped at 1.00) — a fast short-chat sample never vouches for a long chat
· Below 3 samples the deviation shrinks proportionally towards 1.00: one sample can move it at most 1/3
· Sites with real traffic are scored on measured numbers; probe-only sites use the probe tier, capped at 1.00 (probes are a tiny 45-token request plus a 14.5k cache probe — they can prove "not slow", not "faster")
· Nothing measured at all counts as 1.00 (usual level), never 0

Reliability below 0.8 marks a supply unusable for routing. Speed never gates admission — a slow site is not kicked out, its effective cost is simply divided by a smaller number.

Scores expire (6 hours by default). An expired score is not used — stale data is more dangerous than no data, because it makes you think you already checked. Scheduled probing exists to keep scores fresh.

③ Decision: filter first, then compare price

Hard constraints — untrusted or expired: pushed to the back as a last resort.
Effective cost — the rest are sorted by price ÷ quality, ascending.

That "price" is not the number on the site's price list — it is expected cost under your own usage:
· Input share — taken from your real traffic (input tokens ÷ all tokens); 90% until there is data
· Cache discount — input price times 1 − hit rate × 0.9. The hit rate is measured per request by the gateway: cache reads ÷ (net input + cache reads + cache writes), with cold starts (new session, chat content just changed, idle for a while) excluded
· With few samples it is shrunk towards the global usual level, so one outlier cannot decide the ranking

The "untrusted" part can be switched off with Allow suspicious supplies on the Probes page: they then compete on effective cost instead of being pushed back. The switch also changes what Pricing calls "cheapest" and what the Overview concludes, so recommendations and real routing always use the same rule.

Why divide instead of weighting? Because "10% cheaper but 30% dumber" can still win a weighted sum, while dividing by quality doubles the cost when quality halves — no discount can outrun that. The formula is also explainable: it is "what you actually pay for one trustworthy answer".

④ Routing: fall through to the next site

This is the gateway's core value. If the first site for a model is down, the second and third are tried automatically and the client never notices. The tricky part is the streaming boundary: the first chunk must be read and confirmed not to be an error before response headers are committed.

· Failure before the first byte — silently switch, the client sees nothing
· Failure after the first byte — data is already flowing; we can only end with an error, not retry
That is why order matters: the first site must be the most likely to succeed.

⑤ Feedback: real traffic counts too

Probes are synthetic and cannot detect "5xx at peak hours". So every forwarded request also counts toward that site's availability. A site with healthy probes but three consecutive real failures drops to 63% availability, turns "unstable", and is skipped on the next route.

A request where the client hung up early but the upstream had already delivered the whole turn (finish_reason and usage received) is also a valid sample — that is how almost every long chat ends: DSH and similar clients disconnect after the tool call instead of waiting for the final [DONE]. Recent requests shows them as "delivered · client hung up first": counted as success, availability untouched.

Successful real responses are also sampled for two objective signals: empty answers (200, clean finish, not a single character) and billing anomalies — billed input, after subtracting the cache hits of that same request, still more than 4× the estimated request body. Sites commonly count a long system prompt in prompt_tokens; when it hits the cache every time it costs almost nothing, so only the remainder matters. Connection-level failures are treated as a local network problem when two or more sites fail at once, and are then not charged to the site.

⑥ Collection: balance, bills, ratios, notices

Comparison and probes answer "which site is best right now"; collection answers "what happened these past days". Every 30 minutes by default (can be turned off). It only reads site APIs and burns no tokens, so it can be more frequent than probing. Four things per site, each failing on its own:
· Balance — the site's dashboard API, needs a site login session; unreadable shows "no data" rather than a guess
· Actual spend — the site's own daily bill, see Balance overview above
· Group ratios — /api/v1/channels/available, which also brings back base prices
· Upstream notices — deduplicated by title + publish time

On 401/403 it renews once by itself: when a scheduled collection finds the session expired, it renews it automatically and then re-reads that round's bills — you do not have to do anything. Only when the renewal fails (the session is really dead) is it recorded as "bill: <reason>" and the site marked session-invalid.

Alerts cool down per "site × type": the same low balance is recorded once per six hours, otherwise onboarding floods you. The first collection only records a baseline and raises no changes — otherwise you would see a wall of "new" that is really just the initial state. The balance alert threshold is in USD (sites in CNY are converted before comparing); set it to 0 to disable.

Deliberate trade-offs

Latency becomes a relative score, never an absolute gate — TTFT and speed are divided by the usual level of the same model in the same chat-length tier and multiplied into quality instead of being added to price. Absolute values depend too much on local links and chat length; a fixed ceiling only kills good supplies.
Cache hit rate is priced in, from your own measurements and on the input side only — it comes from your per-request ledger, so it reflects how you actually use the API; if your chat content never repeats, the hit rate is 0 and the discount disappears by itself.
Balance is left blank when unreadable — most sites do not expose balance to API keys; the tool will not guess a number.

FAQ

Balance cannot be read? Most sites do not expose a balance endpoint to API keys. Use Account login (or Import session) on the site card, or just type the balance in.
Spend shows "not collected"? Actual spend only recognises the site's own bill (/api/v1/usage). The card names which case it is: no site session yet, session expired, or the site has no billing API. The tool will not pass an estimate off as a bill.
Spend looks lower than expected? The bill only covers traffic this site recorded itself. Anything you sent to the site from another client is outside collection; conversely, gateway-side estimates lose about 26% of tokens, which is exactly why they are never used as spend.
Why is a group chip grey? Colours are inferred from the vendors of the group's models: one vendor colours in, mixed vendors or a group with no models yet stay grey. Grey usually means that key has not synced models — run One-click sync.
Do I have to re-copy the token when it expires? No. Sites connected through Account login or Import session renew themselves (once on 401/403, 10-minute cooldown); sites that cannot auto-renew say why on the card, and re-signing in once is enough.
Reload vs. import official prices? The Reload button in the Group ratios panel writes ratios; the Benchmarks page writes official prices. Prices belong to Benchmarks, discounts belong to the site page.
Why does the same model cost different amounts in two groups? That is normal. Groups sit on top of different upstream channels, so both the base price and the ratio can differ. Picking the right group is what makes the price meaningful.
I picked a group but the price did not change? Two cases: ① the model has no benchmark price, so only an absolute price can be filled (the toast says "N without benchmark"); ② the model is not in that group, so it counts as unmatched.
Can I skip picking a group? Yes, it falls back to the site's base price (ratio 1). That overstates the cost rather than understating it, so the comparison still points the right way.
Why is a result suspicious? The probe found a fingerprint mismatch, truncated output or a billing anomaly (billed input still too high after subtracting the cache hits of the same request). Expand the row on the Probes page to see the raw response.
Do I have to use the gateway? No. Price comparison and probing work on their own. The gateway adds automatic site selection, one key for every site, and per-client usage.
Can I run two instances? No. The daemon refuses a second instance with daemon.lock, so two processes cannot share one data directory.

Where the data lives

Everything is in ~/.manage-api/ on your machine. Nothing is uploaded. Keys are stored encrypted and only their last digits are shown. On startup and every day, the daemon backs up the data into manage-api-backups/ next to it (including master.key; 30 copies kept by default). Restore db.json and master.key together; a db without its key cannot decrypt saved keys.
